# Адреса проверок и пригодность серверов

Актуализация к ТЗ 0.5 от 12 ноября 2026. Обязательна возможность задать собственный HTTPS URL для проверки серверов через выбранный узел, в том числе адрес ресурса, недоступного напрямую в сети пользователя. Предлагаемый пользователем пример — https://www.instagram.com/favicon.ico. Документ описывает план реализации, не готовую функцию.

## Уточнение пользователя: общий профиль Telegram + Instagram

Пользователь подтвердил на практике, что для его сценария проверка Instagram подходит и для выбора серверов Telegram. При явном выборе пользователем общий профиль «Telegram + Instagram» проверяется через пользовательский Instagram URL. После чистой установки этот профиль автоматически не создаётся. Отдельная Telegram-проба не обязательна для допуска и не блокирует первую реализацию. Это выбранная эвристика пригодности группы, а не утверждение о выполненной отдельной протокольной проверке Telegram.

## 1. Два уровня реализации

| Профиль | Назначение | Допуск сервера |
|---|---|---|
| Общий доступ | Обычные сайты | Ожидаемый ответ выбранной нейтральной цели; в расширенном варианте согласованные ответы независимых целей |
| Telegram + Instagram / контрольный ресурс | Общий пул для двух сервисов по проверенной пользователем схеме | Проверка Instagram URL; ответ Google/Apple не заменяет её; отдельная Telegram-проба не требуется |
| Сервисный, расширенный | Instagram, Telegram или другое назначение | Собственные обязательные проверки профиля; результаты других сервисов не подменяют их |

На первом этапе сохраняется существующий выбор одного HTTPS URL для GlobalAuto и добавляется контракт результата тела/данных. Отдельный менеджер двух сохранённых профилей не входит в обязательный объём. Профили «Telegram + Instagram» и «Общий доступ» описывают последующее расширение. После чистой установки действует обычная цель Keqdis, HTTPS GET к `https://connectivitycheck.gstatic.com/generate_204` с ожидаемым 204. Пользователь самостоятельно назначает маршруты, профиль проверки и при необходимости свой HTTPS URL. [Исходные пресеты Keqdroid v0.36.3](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/models/ping_test_config.dart). В каждой форме: пресет либо «Свой URL», кнопка проверки, ожидаемый результат, последний исход и время. Пользователь может выбрать контрольный профиль основным для всего VPN. Отказ на его URL не удаляет узел из подписки: узел может оставаться пригодным для общего доступа.

На этом этапе один активный узел обслуживает общую proxy-цель. Keqdroid уже поддерживает отдельные фиксированные серверы маршрутов. На этапе M4 добавляется независимый автоматический подбор по группам: правило → Auto-группа → профиль проверки. Выбор профиля в GlobalAuto сам по себе меняет проверку общего выхода.

Пресеты общего доступа: проверенные небольшие connectivity endpoints Cloudflare/Google/Mozilla/Apple; точные URL, методы и ожидаемые ответы версионируются и проверяются перед включением. Обычная главная страница менее удобна из-за редиректов, локализации и защиты от ботов. Название провайдера не гарантирует доступность его endpoint. Для общего доступа расширенный профиль допускает критерий 2 из 3 независимых целей; это стартовая политика для измерения, не обязательное требование к каждой сети.

## 2. Границы контрольного ресурса

Не закреплять обещание «100% заблокирован во всей РФ»: технически нужно проверять конкретный адрес из конкретной сети. Сам факт невозможности direct-запроса не доказывает причину отказа. Проверка прямого пути — отдельная опциональная диагностика; не обходить пользовательскую политику запрета прямых соединений ради классификации.

Ответ Instagram/favicon доказывает доступность этого объекта по проверенному пути. Он не доказывает полную работу Instagram, Telegram или всех заблокированных сайтов. Объект может обслуживаться иначе, чем API, медиа и звонки. Российский выход также не исключается по географии автоматически: решает профиль доступа, а запрет страны — отдельная явная политика.

При выборе общего шаблона Telegram и Instagram связываются с одной Auto-группой и одним Instagram-профилем, тест не дублируется. Такая группа относится к дальнейшему расширению. Дополнительно пользователь может разделить их и назначить собственные критерии. Для общей группы «контрольные ресурсы» можно задать несколько URL с явным правилом ANY/ALL. Если пользователь требует конкретный URL, его отказ нельзя скрыто заменить успехом другой цели. Если Instagram не работает, а Telegram проходит собственную проверку, узел остаётся кандидатом Telegram, если пользователь явно не выбрал совместное требование ALL.

Если пользователь включил дополнительный самостоятельный Telegram-профиль, он раздельно показывает Web/API, протокольную доступность и, при наличии реализованной проверки, медиа/звонки. Веб-проверка не называется полной проверкой Telegram. Общая контрольная цель полезна для предварительного обследования, но не является универсальным жёстким фильтром перед всеми сервисными тестами.

## 3. Контракт HTTPS-пробы

- Запрос принудительно проходит через конкретный кандидат/цепочку, без direct fallback и без перенаправления на текущий глобальный узел. Разрешение имени проверяемой цели соответствует этому пути; bootstrap DNS самого proxy-сервера учитывается отдельно.
- По умолчанию GET с TLS-проверкой, общим deadline и лимитом ответа. HEAD допустим только как отдельный явно обозначенный метод с проверенной совместимостью цели.
- Для endpoint 204 проверять ожидаемый статус; тело не требуется. Для файла/favicon — ожидаемый 200, завершение небольшого ответа в лимите, подходящий тип/формат; HTML авторизации или заглушка не становится успешной картинкой.
- Редиректы ограничены, проверяется конечное назначение. Переход на доступный посторонний домен, login/challenge или региональную заглушку не доказывает пригодность сервиса. Набор допустимых redirect hosts задаётся профилем.
- 403/429/5xx, неправильное тело, ошибка DNS, TLS и timeout имеют разные причины. Ответ с ошибкой может подтверждать, что транспорт отвечает, но не прохождение сервисного профиля. Ожидаемый 401 допустим только для специально описанного endpoint, не как общее правило.
- Задержка до заголовков и чтение тела — разные поля; ошибка тела не подавляется. Холодный замер и повтор с keep-alive хранятся отдельно, а не смешиваются в один несопоставимый RTT.
- Проверка большого объёма остаётся отдельной: маленький favicon не доказывает устойчивость загрузки 64–256 KiB и длительной сессии.

Не добавлять произвольные уникальные query-параметры к стороннему URL: они могут менять ответ. Для измерения обходить локальный кэш клиента; для контролируемого canary использовать документированный nonce/ответ. Не отправлять cookies, учётные токены сервисов или пользовательские данные при фоновых проверках.

## 4. Автовыбор и экономия ресурсов

Результат хранится по ключу: идентичность узла/цепочки + hash конфигурации + фактическое ядро + поколение сети + профиль/версия цели + метод + время. Для сервера нет единственного вечного флага «рабочий».

Сначала подтвердить требования выбранного профиля; затем ранжировать прошедших по истории успешности, свежести, разбросу и задержке. Малый RTT к Google не даёт допуска в группу Instagram. Ни успех, ни отказ одной нейтральной цели не заменяют собственные проверки сервиса.

Полный скан — по запросу/постепенно после изменения подписок. В фоне проверять активный путь и небольшой резерв, остальные узлы обследовать по очереди. Сервисные проверки делать для используемых групп и кандидатов; не запускать все сервисы на каждом узле в каждом цикле. Ограничить параллелизм, запросы на домен/аккаунт, трафик и повтор после 429.

Если одна цель одновременно отказывает у ранее независимых рабочих путей, пометить подозрение на проблему цели и перепроверить альтернативной диагностикой. Не удалять все узлы и не запускать бесконечные переключения. При обязательном отказавшем URL профиль остаётся неподтверждённым/непройденным, даже если общий Интернет доступен; автоматической подмены успехом Google нет.

Перед переключением проверить выбранного кандидата, после переключения — реальный активный маршрут с правилами/DNS. Отказ одного сервиса переключает его группу; глобальный туннель не перезапускается без необходимости. Применение отдельных outbound в группе должно поддерживаться адаптером ядра; до этого UI честно предлагает только глобальную смену.

### Допуск для правил БС и ЧС

Требование страны применяется к фактическому выходу всего пути. В БС для российских назначений вне мобильных белых списков требуется подтверждённый выход в РФ. В ЧС для сервисов, ограничивающих доступ из России, требуется подтверждённый выход вне РФ. После подтверждения страны проверить передачу данных по профилю назначения. Для резервного пути действуют те же требования. Прямые маршруты проверяются отдельно по доступности физической сети.

## 5. Приёмка

Первый этап проверяет один выбранный URL, ожидаемый 204, неверное/зависшее тело, редиректы, байтовый бюджет, timeout, смену контекста и оба ядра. Строки с несколькими профилями, группами и самостоятельным Telegram-тестом проверяются на последующих этапах. Успех 204 не называется подтверждением передачи объёма.

| Сценарий | Результат |
|---|---|
| Google работает, контрольный Instagram URL не проходит | Общий доступ проходит; контрольный профиль не проходит; в его Auto узел не выбран |
| Общий TG+Instagram профиль, Instagram прошёл | Узел допущен в общую группу без обязательной Telegram-пробы; показан фактический метод «проверка через Instagram» |
| Включена отдельная Telegram-проверка, она не прошла | Её результат не подменяется успешным Instagram; применяется выбранная пользователем политика |
| Telegram проходит свою проверку, Instagram нет | Telegram может использовать узел, если нет явного совместного требования ALL |
| Файл вернул 200 с HTML/обрезанным телом | Проверка объекта не проходит |
| Ожидаемый 204 | Успех без обязательного скачивания тела |
| Редирект на другой доступный сайт / direct-правило для цели | Не принимается за успешную принудительную пробу кандидата |
| Цель отдаёт 429/падает сразу на нескольких путях | Backoff/диагностика цели; нет удаления всех узлов или шторма смен |
| Сменились URL/критерии/сеть/ядро | Старые результаты не дают актуального допуска |
| Два ядра проверяют один профиль | Одинаковые критерии статуса/тела, различия транспорта явно учтены |

Текущие URL пользователя и доступность из его сети самостоятельно не измерялись. Источники: [sing-box URLTest](https://sing-box.sagernet.org/configuration/outbound/urltest/) описывает одну URL-цель; [mihomo expected-status](https://wiki.metacubex.one/en/config/proxy-groups/#expected-status) задаёт ожидаемый HTTP-код. Их наличие не заменяет контракт тела и сервисных возможностей Orrdroid. [Telegram MTProto](https://core.telegram.org/mtproto) отдельно описывает протокол клиентских соединений.
