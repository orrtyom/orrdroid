# Синхронизация Orrdroid: два режима и несколько каналов

Статус: ТЗ, редакция 0.4 от 11 ноября 2026. Пользователь расширил модель: поддержать защищённое главное устройство и альтернативную синхронизацию последних изменений со всех устройств. Режим полномочий выбирается отдельно от транспорта.

Согласно редакции плана 0.5 межустройственная синхронизация и встроенный Tailnet относятся к следующим этапам. Первый этап сохраняет и расширяет локальный backup/restore Keqdroid.

## 1. Режимы группы

| Режим | Где редактируются общие настройки | Как распространяются изменения |
|---|---|---|
| Главное устройство | Только на главном | Главное подписывает ревизию; остальные получают и применяют |
| Все устройства | На каждом устройстве с правом записи | Подписанные изменения объединяются; для одного поля учитываются порядок изменений и конфликты |

### Главное устройство

Ровно один издатель. Ведомое не может переписать главное ни через прямой запрос, ни через облачный файл, импорт или подделанную более новую метку времени. На ведомом общий управляемый слой доступен только для чтения. Можно явно создать независимую локальную копию/выйти из группы; эта копия не отправляется обратно.

Отдельный ключ подписи главного не передаётся ведомым. Они получают открытый ключ, права чтения назначенного профиля и ключи расшифрования. Главное офлайн — ведомые продолжают работать с последней проверенной конфигурацией, не избирают нового главного. Отчёты доставки не меняют настройки.

### Все устройства: последние изменения

У каждого участника собственная идентичность и ключ подписи. Право записи выдаётся при сопряжении; возможны участники только для чтения. Изменения из офлайна сохраняются локально и передаются при восстановлении связи.

«Последнее изменение» относится к отдельному объекту/полю, а не ко всему backup. Изменение подписки на телефоне и маршрута на компьютере должны сохраниться оба. Снимок старого телефона не может заменить всю актуальную конфигурацию только из-за более позднего времени загрузки файла.

Предлагаемый контракт слияния для проверки в прототипе:

- Стабильные ID у подписок, групп, правил и цепочек. Каждая операция имеет operation ID, ID автора, эпоху группы, счётчик автора и причинный контекст. Повторная доставка идемпотентна.
- Правка, сделанная после получения предыдущей версии поля, заменяет её. Причинный порядок важнее часов устройства.
- При независимых одновременных правках одного поля — детерминированный LWW-регистр с гибридной меткой времени и ID автора для разрешения равенства. Это правило сходимости, не гарантия того, кто физически нажал кнопку позже на разных устройствах. Обе версии сохраняются в журнале; пользователь может восстановить проигравшую отдельной новой правкой.
- Большой скачок часов, неизвестная эпоха или некорректный счётчик дают конфликт/карантин, а не автоматическую перезапись. Точные пределы и формат часов фиксируются ADR до реализации.
- Удаления — tombstone с версией. Долгий офлайн не воскрешает удалённые объекты. Сборка tombstone допускается после подтверждённого checkpoint участников либо исключения старого устройства с обязательным новым bootstrap.
- Порядок маршрутов — версионируемый список ID, применяемый атомарно. Одновременные перестановки фиксируются как конфликт; не складывать числовые order независимо, создавая дубликаты/неопределённый приоритет.
- Ссылки на удалённые группы/серверы, несовместимые правила и конфликт секретов не применяются частично. Сохраняется last-known-good, показывается причина и варианты разрешения. Автоматическое слияние никогда не включает direct fallback незаметно.

Формат репликации и библиотека выбираются после тестирования. Название «по последним изменениям» не означает доверие mtime файла, системным часам или времени ответа облака.

### Смена режима и управление участниками

Режим действует на всю группу. Он не переключается автоматически при исчезновении главного или конфликте. Переход из режима главного во все устройства подтверждается владельцем на главном, создаёт новую подписанную эпоху и явно выдаёт права записи. Обратный переход назначает главное и подтверждает исходный снимок; неприменённые правки сохраняются для просмотра.

При утрате главного — заранее подготовленная процедура восстановления либо повторное сопряжение; ведомое не повышает себя самостоятельно. Полномочия, отзыв устройств, смена режима и ключей не разрешаются обычным LWW-слиянием. Владение группой и редактирование её конфигурации — разные права. Старые операции после смены эпохи/отзыва не применяются автоматически.

## 2. Синхронизируемые данные и локальный слой

| Данные | Политика |
|---|---|
| Подписки, URL и необходимые credentials | Шифрованный общий профиль только назначенным участникам |
| Узлы подписок | Режим главного: обновляет главное. Все устройства: отдельные результаты refresh с происхождением и revision/hash; не смешивать два provider snapshot по отдельным узлам |
| Ручные узлы, AWG, группы, цепочки, маршруты, порядок, provider overrides, hosts-списки | Стабильные ID; синхронизация декларативной конфигурации |
| Политика Auto и профили сервисных проверок | Общие настройки, допускающие явный профиль устройства |
| Активный узел, ping, история отказов, режим физической сети, DNS-кэш, резерв Auto | Локальные результаты; не навязываются другому устройству |
| Приложения и пути процессов | Платформенные привязки; неизвестная привязка не становится правилом для всех приложений |
| MTU, интерфейсы, порты, UI и энергосбережение | Локальный слой либо явно назначенный профиль |
| Включение LAN-прокси, bind-адрес, пароль раздачи | Локально; обычная синхронизация никогда не открывает listener на другом устройстве |
| Tailscale node state/private key, signing keys устройств, keystore | Не клонировать в обычном backup/sync |
| Tailscale Auth key и токены внешнего хранилища | Настройка канала при сопряжении; не распространять как общую настройку подписок |

В режиме всех устройств планировщик ограничивает дублирующиеся refresh подписки. Снимки одного источника имеют base revision; разные ответы вследствие UA/HWID/платформы не должны незаметно заменять общий набор. Сохранять выбранный общий профиль либо локальный platform overlay; спорные снимки показывать как конфликт. Повторный provider refresh не считается пользовательской правкой URL/правил.

Не предполагается право использовать одну подписку на любом числе устройств: персональные учётные данные и лимиты обслуживаются назначенными профилями.

## 3. Каналы обмена

Оба режима работают поверх общего формата операций/снимков, не привязанного к одному каналу.

| Канал | Применение | Требование / ограничение |
|---|---|---|
| Tailnet | Автоматически между разными сетями без публичного порта | Предпочтительный транспорт; userspace-интеграция при одном Android VpnService; отдельное сопряжение Orrdroid |
| Локальная сеть | Прямой обмен телефон–планшет–ПК–ТВ в одной сети | TLS с закреплением ключа после QR/кода; ручной адрес обязателен, mDNS опционален. Обнаружение не выдаёт полномочий |
| Резервная копия/файл | Ручной офлайн-перенос или начальное восстановление | Шифрованный экспорт; предварительный просмотр diff; нельзя обойти режим главного импортом чужого файла |
| WebDAV/Nextcloud | Автоматический обмен через внешнее хранилище | Приоритетный облачный адаптер для оценки; только клиентское шифрование/подписи; корректность не зависит от порядка загрузок |
| S3-совместимое хранилище | Самостоятельно размещённое или облачное хранилище объектов | Опциональный адаптер после прототипа; отдельные ключи доступа и immutable объекты |
| Синхронизируемая папка / Drive / OneDrive и аналоги | Дополнительный транспорт файла либо отдельная интеграция | Проверить API, фоновые ограничения и конфликтные копии на каждой платформе; не обещать поддержку всех сервисов первым выпуском |

Внешний сервис хранит зашифрованные объекты и не получает ключи расшифрования. Не строить multi-writer на одном изменяемом файле: параллельные uploads теряют правки. Использовать отдельные журналы/объекты по устройствам, manifest и checkpoint, проверять пропуски, дубли и rollback. Для WebDAV/S3 протестировать возможности условной записи и реальную семантику выбранного сервиса; не полагаться на универсальную атомарность.

Обычный backup без истории репликации импортируется как новая локальная операция с preview, а не как «самая новая версия всей группы». На ведомом в режиме главного нельзя импортом перезаписать управляемые настройки. Backup для восстановления и транспорт синхронизации файла — разные сценарии UI.

В Tailnet listener привязан к Tailnet. В LAN-режиме включается отдельный защищённый sync endpoint на выбранном интерфейсе; он не открывается автоматически вместе с SOCKS/HTTP-раздачей. Без LAN-режима синхронизация не слушает Wi-Fi. Можно использовать несколько каналов без двойного применения операции.

## 4. Проверка и применение

Стандартные криптобиблиотеки; шифрование payload и подпись автора/издателя. Envelope: group ID, эпоха, автор, operation/revision ID, схема, минимальная версия клиента, hash, причинный контекст и назначение профиля. Проверять полномочия, подпись, целостность, anti-replay, лимиты размера и совместимость до подготовки конфигурации.

Полученная, объединённая и применённая версии отображаются отдельно. Проверка ссылок/схемы → dry-run генератора ядра → атомарное применение → подтверждение активного пути/откат. Перезапуск туннеля из-за обычного обновления откладывается до разрешённого момента; срочные изменения имеют отдельную явную политику. Ошибка оставляет last-known-good и журнал причины.

Предусмотреть историю правок, просмотр конфликтов, восстановление выбранной версии, «Синхронизировать сейчас», последнюю успешную связь и причину ожидания. Не показывать «синхронизировано», если документ получен, но ещё не применён.

## 5. Сопряжение, офлайн, отзыв и транспорт AWG

Первый QR/код содержит ограниченные bootstrap-данные и pin ключа, а не долгоживущий reusable admin key. Подключение не зависит от ещё не полученных Tailnet/AWG-настроек. Каждый Tailscale-узел имеет собственную идентичность; Auth key регистрации не является ключом подписи Orrdroid.

Офлайн все устройства используют последнюю рабочую конфигурацию; в multi-writer разрешены локальные правки, в режиме главного — только на главном. Фоновую доступность телефонов в Doze/OEM проверять; облачный посредник может хранить уже опубликованный снимок при выключенном главном, но не создавать новую авторитетную ревизию.

Отзыв блокирует будущие операции/получение новых ключей; ротировать ключи при необходимости. Нельзя гарантировать удаление уже выданных данных с офлайн-устройства. Замена главного — отдельная подписанная эпоха и процедура восстановления.

Изменение AWG-параметров канала требует staged activation и пути восстановления для офлайн-участников. Команда tailscale awg sync форка LiuTangLei не заменяет репликацию конфигурации Orrdroid. Полный сетевой паритет Tailscale/AWG остаётся отдельным этапом.

## 6. Этапы

- M3S-A: общий формат, identity/сопряжение, режим главного, LAN и защищённый backup; Android↔Android, затем desktop/Android TV.
- R2a: встроенный Tailnet как транспорт того же протокола без второго VpnService; может разрабатываться независимо от LAN.
- M3S-B: все устройства, офлайн-правки, слияние, tombstone, конфликты, смена режима и отзыв.
- M3S-C: WebDAV, затем выбранные сервисы/папки после испытания их семантики. S3 и фирменные облачные SDK — дополнительные адаптеры, не обязательное условие первой версии.

Оба режима входят в целевой объём ТЗ. Порядок этапов не означает отказ от multi-writer. Полные тесты — VALIDATION.md; роли не смягчаются ради доступности транспорта.
