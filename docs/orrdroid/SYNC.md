# Синхронизация Orrdroid через Tailnet

Статус: проектирование. Основано на уточнениях пользователя: автоматический перенос настроек и подписок между устройствами; одно главное устройство; его конфигурация не может быть переписана ведомыми; предпочтительный канал — Tailnet.

## 1. Модель полномочий

В группе ровно один издатель — главное устройство. Владелец редактирует общую конфигурацию локально на нём. Ведомые получают подписанные версии и не имеют API для изменения конфигурации главного. Сообщения о доставке/ошибках, если будут нужны, хранятся как диагностические данные и не меняют настройки.

Нет last-write-wins, двусторонней синхронизации, автоматического избрания главного или слияния настроек с ведомого. Офлайн-редактирование ведомым общих управляемых настроек запрещено. При необходимости пользователь явно создаёт независимую локальную копию/выходит из управления; она не отправляется группе.

У главного отдельный ключ подписи. На ведомые передаётся только открытый ключ и право чтения назначенного им профиля. Ключ издателя не входит в обычный синхронизируемый backup. Даже скомпрометированное ведомое, имеющее сетевой доступ и ключ расшифрования своего профиля, не может создать подписанную авторитетную версию.

Это защита от обратной синхронизации и подделки публикации, а не обещание защиты от компрометации самого главного устройства.

## 2. Что передаётся

| Данные | Политика |
|---|---|
| URL подписок, необходимые credentials, список разрешённых источников | Передаются зашифрованными только назначенным устройствам |
| Снимок узлов, обновлённый главным | Передаётся как версия конфигурации; последнее рабочее содержимое доступно без повторного обращения каждого устройства к провайдеру |
| Ручные серверы и конфигурации, в том числе AWG | Передаются только если включены владельцем в общий профиль |
| Группы, цепочки, правила, provider overrides, пресеты, URL hosts-списков | Общая декларативная конфигурация со стабильными ID и пользовательским порядком маршрутов `order` из Keqdroid 0.36.1 |
| Политика Auto, пороги и профили проверки | Общие настройки с разрешёнными главным вариантами для типов устройств |
| Текущий сервер, измеренные задержки, история отказов, режим физической сети | Локальные данные; не переносить выводы телефона на Wi-Fi компьютера |
| Package names/пути процессов и системные разрешения | Отдельная платформенная привязка; неизвестные приложения не подменять правилом «для всех» |
| MTU, интерфейс, режим энергосбережения, локальные UI-настройки | Локальный слой либо профиль устройства, явно назначенный главным |
| Tailscale node state/private key, ключ издателя, системные keystore-ключи | Никогда не клонировать в обычной синхронизации |
| Auth key регистрации в Tailnet | Ввод/получение при сопряжении; не распространять reusable admin key вместе с обычными настройками |

Главное устройство обновляет управляемые подписки и публикует новый снимок. Самостоятельное обновление провайдерских узлов на ведомом по умолчанию отключено, чтобы разные списки не выдавались за одну версию. Если позднее нужен режим локального refresh, он должен быть явно разрешён главным и отделён от авторитетного снимка; обратно результаты не записываются.

Подписки с лимитом устройств или персональными ключами требуют отдельных назначенных профилей. Синхронизация не означает, что провайдер допускает одновременную работу всех устройств с одним аккаунтом.

## 3. Передача через Tailnet

Главное публикует manifest и зашифрованный snapshot через встроенный Tailnet-listener. Слушать только Tailnet, не открывать сервис на Wi-Fi/LAN/публичном интерфейсе. Ведомые выполняют pull при подключении к Tailnet, запуске/возврате приложения и периодически с backoff. Уведомление о новой версии можно добавить как оптимизацию; корректность от него не зависит.

Tailnet даёт канал связи и идентичность сетевых узлов, но права группы Orrdroid проверяются отдельно. Нужны явное сопряжение и назначение профиля; любой участник Tailnet не должен автоматически получать секреты подписок. Ограничить доступ ACL/grants и проверять идентичность на стороне приложения.

Шифрование payload и подпись выполняются стандартными проверенными криптобиблиотеками. Ключи чтения лучше назначать устройствам/профилям, чтобы отзыв одного устройства не требовал выдавать всем один вечный общий секрет. Конкретный формат криптоконтейнера фиксируется ADR и проверяется до реализации; самодельные алгоритмы не использовать.

Manifest включает group ID, ID издателя, эпоху полномочий, монотонный номер ревизии, версию схемы, минимальную версию клиента, hash payload, целевое устройство/профиль и подпись. Часы не являются источником порядка. Повтор более старой ревизии отвергается; восстановление после переустановки требует подтверждённого checkpoint/сопряжения, а не доверия первому попавшемуся старому файлу.

Пример обычного обновления: владелец меняет правило на главном → проверяется общий документ → публикуется новая ревизия → ведомое скачивает её → проверяет отправителя, подпись, целостность и совместимость → готовит конфиг своего ядра → применяет в допустимый момент → сохраняет last-known-good.

Если требуется перезапуск активного туннеля, обычное обновление откладывается до безопасного момента или показывает статус ожидания. Срочность может задаваться политикой главного. Ошибка применения оставляет предыдущую рабочую версию; полученная и применённая ревизии показываются отдельно.

## 4. Главное устройство офлайн и восстановление

Ведомые продолжают работать с последним проверенным снимком. Они не назначают нового главного и не объединяют локальные изменения. При его возвращении получают последнюю версию; промежуточные snapshots можно пропустить, если миграция поддерживает переход.

Если главным является телефон, доступность его фонового listener в Doze/OEM-ограничениях нужно измерить. Нельзя обещать мгновенную круглосуточную доставку с выключенного/уснувшего телефона. Постоянно включённый компьютер может быть главным по выбору владельца; автоматически менять роль нельзя.

Смена главного при доступном старом: явное действие владельца, передача полномочий с новой эпохой, подпись старого издателя и закрепление нового ключа. Старый издатель больше не принимает роль публикации. При утрате старого — отдельная процедура восстановления по заранее сохранённому recovery-секрету либо ручное повторное сопряжение всех ведомых. Ведомое не повышает себя до главного самостоятельно.

Отзыв устройства запрещает будущую загрузку; при необходимости ротируются ключи чтения и секреты подписок. Уже выданную конфигурацию нельзя гарантированно стереть с офлайн/скомпрометированного устройства. Это ограничение показывается владельцу при отзыве.

## 5. Bootstrap и изменение транспорта

Первое подключение не может зависеть от ещё не полученных Tailnet/AWG-настроек. Сопряжение передаёт минимальные bootstrap-данные по QR/локальному защищённому обмену: идентификатор группы, pin открытого ключа главного, адрес/идентичность и разрешённый способ входа. Tailscale Auth key и ключ издателя — разные сущности. Auth key не коммитится и не пишется в журнал.

Общий интерфейс Auth key взять как ориентир из Karing; пригодность его sing-box-интеграции для другой архитектуры проверить отдельно. Первоначально можно использовать стандартный транспорт Tailnet; AWG включается только после совместимого bootstrap обоих концов.

Нельзя менять AWG-параметры канала синхронизации так, чтобы главное уже перешло на новые, а офлайн-ведомые не могли их узнать. Для этого требуется отдельный протокол staged activation, срок совместного перехода и проверенный канал восстановления. Если безопасный переход не реализуем, изменение транспорта проводится владельцем при сопряжении, а не как незаметное фоновое обновление.

Команда `tailscale awg sync` у LiuTangLei синхронизирует параметры AWG с peer; это не готовая синхронизация подписок Orrdroid и не гарантия роли главного. Её обнаружение peers нельзя автоматически использовать как выбор издателя.

## 6. Платформы и этапы

Сначала два Android-устройства, затем Android ↔ Windows/Linux. ТВ: Android TV/Google TV, с проверкой ввода Auth key/QR, работы пульта и восстановления после сна. macOS/iOS/tvOS, Tizen и webOS не считаются поддержанными только потому, что Tailscale существует на этих системах; для Orrdroid нужны отдельные сборки/адаптеры.

R2a проверяет транспорт; M3S — протокол полномочий, хранение и применение. Полная интеграция Tailnet как цели произвольного трафика и AWG-транспорт форка рассматриваются отдельно в R2b/M6. Приёмочные сценарии — в VALIDATION.md.
