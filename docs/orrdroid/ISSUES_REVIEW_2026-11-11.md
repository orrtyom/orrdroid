# Karing и Farvater: issues, связанные со стабильностью

Проверено 11 ноября 2026. Просмотрена последняя страница из 50 записей Karing (без включения PR в выводы), выполнен дополнительный поиск по REALITY verification failed и auto select, прочитаны выбранные обсуждения и ответы. У Farvater API вернул три issue; прочитаны все и комментарий к #1. Это тематический обзор, не аудит всех исторических ошибок и не самостоятельное воспроизведение.

## Farvater

- [#1](https://github.com/farvater-app/farvater/issues/1): открытый запрос автоматического переключения после отказа. В проверенном коде v1.0.31 механизм уже есть: autoSwitch, Failover и мониторинг VPN service. Поэтому открытый статус не означает отсутствия функции в текущей версии. Публичного подтверждения автора issue о результате использования нет.
- [#2](https://github.com/farvater-app/farvater/issues/2) и [#3](https://github.com/farvater-app/farvater/issues/3): открытые запросы исключать страны из автоматического выбора. Пользователь сообщает, что низкая задержка выбирает неподходящий для игры российский выход. В #3 подчёркнуты сохранение фильтра после обновления и запрет автоматически нарушать исключение, когда других узлов нет. В прочитанных обсуждениях нет подтверждения реализации.

Малое число issues Farvater не доказывает превосходство стабильности. Его backup не содержит результатов пингов/резервов и не позволяет сопоставить пользовательские жалобы с собственным текущим замером.

## Выводы для Orrdroid

1. Диагностировать по этапам: импорт/выдача провайдера → DNS узла → TLS/REALITY → HTTP → тело → фактический маршрут. Не превращать всё в Connect Timeout.
2. Сохранять обезличенную сводку импорта: тип ответа, число полученных/распознанных/отклонённых узлов, причину пропуска, профиль UA и DNS; секреты не журналировать.
3. Проверять совместимость REALITY на матрице серверных версий и ClientHello-профилей; не копировать спорный патч без регрессий.
4. Применять результаты Auto независимо от удаления нерабочих узлов. Удаление не должно быть обязательным для переключения; stale callbacks после обновления списка отменяются.
5. Группы/маршруты имеют стабильные ID и переживают обновления, синхронизацию и удаление текущего узла. Конфликт показывается, не маскируется переключением на глобальный путь.
6. Поддержать положительные и отрицательные ограничения страны выхода. При отсутствии допустимых узлов — явное отсутствие кандидатов, без молчаливого снятия запрета; название/флаг узла не является подтверждённой географией выхода.
7. Сохранять crash-логи при перезапуске; испытывать сутки работы, повторные переподключения, обновление подписки во время проверки и изменение DNS/сети.

См. [сравнение актуальных backup](BACKUP_COMPARISON_2026-11-11.md). Ни один issue авторами этого отчёта не создавался и не комментировался.
