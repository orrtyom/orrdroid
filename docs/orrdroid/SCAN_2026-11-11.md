# Разбор резервной копии и RKNHardering от 11 ноября 2026

Статус: анализ предоставленных файлов и исходного кода. Это не собственное испытание устройства и не подтверждение полной изоляции. База проекта — Keqdroid v0.36.1 по указанию пользователя; формат backup `keqdis_backup`, version 1 сам по себе не подтверждает версию установленного APK.

Исходные файлы: backup с временем экспорта 06:41:34 и скан RKNHardering 2.11.0 с меткой 06:40:21+03:00. У backup нет часового пояса; близость имён/времени не доказывает неизменность активного VPN между сканом и экспортом. Секреты, адреса узлов, идентификаторы подписок, IP и перечень пользовательских приложений в этот документ не включены.

## 2. Что действительно показал скан

| Проверка | Результат | Граница вывода |
|---|---|---|
| Контекст сканера | Управляемый рабочий профиль / вторичный пользователь | Контекст Keqdroid отдельно не доказан |
| Android TRANSPORT_VPN | Не виден сканеру | Не означает отсутствие VPN в другом профиле |
| Нативные интерфейсы и маршруты | tun0 виден, MTU 1400, маршрут через tun0 | Подтверждает обнаружимость, а не передачу чужого трафика |
| SO_BINDTODEVICE | setsockopt успешен, getsockopt подтверждает | Только установка параметра сокета |
| Активные TUN-пробы | ip.mail.ru и api4.ipify.org: Android Network binding EPERM; подключение через tun0 не удалось | Успешная передача через чужой TUN в этих пробах не показана |
| Localhost/API | Открытые прокси, Xray gRPC и Clash/sing-box REST не обнаружены; proxyChecks пуст | Отрицательный результат в контексте этого скана, не гарантия для всех профилей/портов |
| Bypass | detected=false, needsReview=true; vpnNetworkIp отсутствует | Сравнение VPN/underlying неполное |
| Публичные IP | Два разных IPv4 в канале DIRECT; foreignIps пуст; crossChannelMismatch=false | Это не сравнение подтверждённых direct/proxy-выходов |
| Beta | 14 AVAILABLE, 16 UNAVAILABLE, 4 PERMISSION_DENIED, 2 ERROR, 2 UNSUPPORTED | Значительная часть проверок не выполнена успешно |

Yandex IPv4 и underlying-проверка дали адрес A; другие ответившие IP-чекеры и GeoIP — адрес B. Некоторые чекеры не ответили: например, 2ip.ru вернул 404 с сообщением о переходе на 2ip.io; IPv6-пробы не прошли. Разные адреса могут требовать проверки маршрутов/выходов, но установить причину по этому скану нельзя. Наличие direct-правил Keqdroid не доказывает, что трафик сканера из рабочего профиля вообще обрабатывался этим клиентом.

Неудача TUN-проб согласуется с ограничением доступа, но не позволяет приписать результат именно owner guard: возможны ограничения Android, профиль, недоступность цели или иные условия. Нужны контрольные успешные запросы и логи соответствующего ядра.

## 3. Почему сводка выглядит тревожнее исходных результатов

Проверен код тега RKNHardering v2.11.0.

1. **DETECTED по R2.** `VerdictEngine.evaluateBetaRule` объединяет обнаруженный изолированный профиль с независимым стабильным сетевым признаком. В данном скане beta evidence содержит BETA_USER_PROFILE, а indirect evidence — интерфейс/маршруты. Для ветви `isolated_context_plus_network_signal` успешная передача через туннель не требуется. Название домена NETWORK_PATH_DIVERGENCE здесь не означает измеренное расхождение двух успешных путей.
2. **Ошибочная подпись «IP через VPN Network».** `VerdictNarrative.collectSnapshot` при отсутствии структурированного vpnNetworkIp берёт первый IP из текста finding с источником VPN_NETWORK_BINDING/TUN_ACTIVE_PROBE, не проверяя detected. В предоставленном файле выбран finding о неполном сравнении, где указан только адрес вне VPN. Локальное воспроизведение выбора подтвердило: полученный адрес совпадает с underlyingIp, detected=false, vpnNetworkIp отсутствует.
3. **Ошибочная причина «Найден локальный proxy».** `buildReasonRows` добавляет строку narrative_reason_bypass_unconfirmed по одному bypassResult.needsReview. Русская строка сообщает о найденном proxy, хотя наличие endpoint или положительной пробы не проверяется. В данном файле proxyChecks и bypass evidence пусты, findings сообщают, что открытые прокси не найдены.

Это дефекты сводки, а не доказательство того, что все признаки детектора ошибочны: видимость tun0 подтверждена независимо.

## 4. Изменения критериев Orrdroid

- Ранняя R1 проверяет три отдельных результата: видимость VPN, прохождение запрещённого трафика, доступ к proxy/API. Общий вердикт стороннего сканера не является воротами выпуска.
- К успешной передаче предъявляется доказательство: запрос с уникальным nonce, ожидаемый ответ и журнал контролируемой цели. Успешный bind, TCP handshake или ответ с непроверенным телом не заменяет это доказательство.
- Для отрицательной пробы нужен положительный контроль доступности той же цели через разрешённый путь; иначе результат «неопределённо», а не «защищено».
- Матрица: тот же профиль и другой профиль; allProxy/include/exclude; Xray/mihomo; TCP, UDP, DNS, IPv4/IPv6; работа и отказ owner lookup. В текущем split-сценарии ownerGuardFor должен включать защиту при Android TUN и SDK>=29, но реальная сборка и исполнение требуют проверки.
- GlobalAuto хранит раздельно результаты нейтральных целей, сервисных целей и проверки тела. Сбой Instagram/favicon не делает все узлы неисправными для других сервисов. После выбора проверяется фактический активный маршрут с правилами, DNS и цепочкой.
- Для миграции добавить синтетический backup с пятью маршрутами без order; проверить вычисленный порядок и экспорт/импорт на обоих ядрах. Отсутствие order допустимо и само по себе не является ошибкой.
- Диагностика хранит структурированные поля пути, метода, статуса, адреса, объёма и причины ошибки. Не извлекать подтверждённый VPN-адрес из свободного текста; не заменять null/unknown на успех или отказ.
