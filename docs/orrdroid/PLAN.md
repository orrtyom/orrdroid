# Orrdroid: план создания форка

Редакция плана: 0.4. База для импорта: Keqdroid v0.36.1, commit `eca4c926f096731fec3f6746c15625c53b1c6573`. Исследование v0.36.0 дополнено сравнением изменений до v0.36.1. Документ описывает проектируемое поведение, а не уже работающие функции Orrdroid.

## 1. Цель и принятые решения

Создать Android-клиент, который сам поддерживает пригодное для работы соединение: определяет состояние сети, проверяет узлы всех разрешённых подписок, выбирает устойчивый путь и меняет его при подтверждённом отказе либо устойчивом существенном улучшении. Пользователь должен понимать причину выбора и иметь простой ручной режим.

Приоритеты: доступность нужного сервиса → отсутствие лишних переключений → восстановление после сбоя → расходы батареи и трафика → задержка и скорость.

Для первой версии принимаются Android без root и сохранение совместимости существующих конфигураций Keqdroid. Новые функции сначала проверяются на Android; поддержка настольных платформ требует отдельной приёмки. Сохраняются Xray и mihomo: выбор ядра определяется возможностями конфигурации. Нельзя обещать, что каждый импортированный протокол работает через Xray.

Из Keqdroid использовать существующие адаптеры ядер, импорт, пакетные замеры, историю, модели подписок, цепочки и маршруты. Из Farvater взять подход к определению состояния сети и проверке передачи данных. Из Karing — идею независимых групп автовыбора как целей маршрутизации. Заимствование идеи не означает прямое копирование реализации другого ядра.

Практические наблюдения пользователя важнее привлекательности алгоритма по исходникам. Любое заявление о повышении стабильности должно подтверждаться сравнением на одинаковых условиях. В предыдущих бэкапах состав подписок и параметры тестирования различались; их сохранённые результаты не являются чистым A/B-тестом.

## 3. Что уже есть в Keqdroid

По v0.36.0 и сравнению с v0.36.1 [S1–S6, S18]:

- Автовыбор использует историю задержек, разброс и отказы; при успешной проверке текущего узла сохраняет его. Основная область выбора — подписка, резервирование включает соседние подписки в порядке списка. Это не равнозначно глобальному поиску по всем подпискам.
- Есть ограничения частоты переключений и замедление проверок при массовом отсутствии ответов. Их полезно сохранить, уточнив классификацию причин сбоя.
- Android URL-проба делает GET, измеряет время до заголовков и может выполнять два запроса с выбором меньшего времени. Ошибка дочитывания тела подавляется. Такую метрику нельзя считать подтверждением устойчивой передачи данных.
- Уже существуют цепочки конкретных серверов, URL-списки/hosts, маршруты приложений и доменов, профили подписок, Xray и mihomo. Расширять эти механизмы с миграцией, а не создавать параллельные несовместимые модели.
- AmnesiaWG уже поддерживается через mihomo, в том числе как совместимая ступень цепочки. Это подтверждено `vpn_core_support.dart` и fixture `chain-reality-awg-hy2.json` [S15]. Наличие AWG-профиля не означает, что встроенный Tailscale автоматически использует его.
- В релизе заявлены фильтрация опасных секций импортированного Xray-конфига, защита управления VPN от других приложений и проверка подписей обновлений. Провести регрессионную проверку этих мер, не выдавать их за новые функции форка.

В v0.36.1 уже добавлен ручной порядок маршрутов раздела «все приложения»: поле `TrafficRoute.order`, перемещение обычных и профильных правил, применение порядка в Xray/mihomo и связанные изменения DNS Xray. Не реализовывать эту функцию повторно. Сохранять порядок при импорте, синхронизации, обновлении подписок и добавлении целей-групп.

Рабочие точки расширения: `auto_server_select.dart`, `auto_select_watchdog.dart`, `vpn_state_provider.dart`, `ping_service.dart`, `EphemeralXrayPing.kt`, `traffic_routes.dart`, `proxy_chain.dart`, `rule_lists_provider.dart`. Это ориентиры на исходной версии; окончательную декомпозицию выбрать после импорта и запуска базовых тестов.

## 4. Архитектура

Разделить принятие решений и исполнение. Алгоритм должен воспроизводиться на сохранённой последовательности событий без реального VPN. Сервис Android отвечает за жизненный цикл и исполнение проверок; интерфейс показывает состояние. Закрытие экрана Flutter не должно останавливать мониторинг. Выбор фонового Dart isolate либо нативного исполнителя делается после проверки текущей архитектуры; двух независимых управляющих циклов быть не должно.

| Компонент | Ответственность |
|---|---|
| NetworkContext | Физическая сеть, её поколение, режим, уверенность, доступность DNS и контрольных адресов |
| ProbeScheduler | Очереди, приоритеты, таймауты, отмена, лимиты трафика и параллелизма |
| ProbeRunner | Тест конкретного узла/пути через совместимое ядро, без подмены действующим туннелем |
| HealthStore | История, свежесть, ошибки, подтверждённые возможности, контекст измерения |
| CandidateSelector | Допуск кандидатов и ранжирование отдельно от переключения |
| AutoController | Состояния отказа, восстановления и улучшения; единственное решение о переходе |
| RouteCompiler | Единая модель правил → конфиг ядра; проверка возможностей и объяснение маршрута |
| SwitchExecutor | Подготовка кандидата, применение, проверка нового пути, откат |

Новые сущности: `NetworkContext`, `ProbeProfile`, `ProbeResult`, `NodeHealth`, `SelectionPolicy`, `ServerGroup`, `ChainTemplate`, `RouteTarget`, `SwitchEvent`.

Результат проверки хранит ID узла/цепочки, hash существенной конфигурации, ядро и его версию, поколение сети, профиль проверки, время, этап ошибки, HTTP-код, число байт, время первого байта и передачи. Историю разных сетей, ядер и целей проверки нельзя слепо смешивать. Смена credentials/транспорта инвалидирует прежнее подтверждение; переименование сервера — нет.

При переходе между подписками активный пользовательский набор маршрутов сохраняется. Зависимости правил/DNS от подписки разрешаются явно. Автовыбор не должен незаметно менять политику доступа вместе с сервером.

## 5. Определение режима сети

Пользовательские режимы: Авто, БС, ЧС. Внутренние состояния дополнительно различают неизвестную сеть, отсутствие связи и captive portal. «БС» — рабочая гипотеза по доступности целей, а не достоверное определение политики оператора.

Проверять несколько независимых контрольных целей непосредственно через выбранную физическую сеть. Проверки через VPN не показывают режим underlying-сети. Не использовать одну Instagram/Google/Cloudflare-цель как единственный критерий.

Решение опирается на сетевые callbacks, доступность нескольких локальных и внешних целей, ожидаемый статус/ответ и фактически прочитанные данные. Не считать любой HTTP-ответ успешным Интернетом. Несогласованные результаты дают «неизвестно», а не принудительный БС.

Первоначальные параметры для испытаний: задержка 3–5 секунд после смены сети, подтверждение изменения двумя раундами; ручной режим имеет приоритет над автоматикой. При неопределённости сохранять последний подтверждённый режим как подсказку и явно показывать его давность. Не исключать все узлы только из-за слабой гипотезы о режиме.

Узел может быть заявлен провайдером как БС, но это лишь метка. Фактическая пригодность хранится отдельно, по сети и времени. Узлы с неизвестной пригодностью получают ограниченный бюджет исследовательских проверок.

## 6. Проверки работоспособности

| Уровень | Что проверяет | Когда применять |
|---|---|---|
| Быстрая URL-проба | Реальное соединение через узел, ожидаемый HTTPS-ответ | Первичная проверка списка, периодическая проверка активного пути |
| Проверка данных | Ограниченный GET с чтением заданного объёма и проверкой содержимого/длины | Допуск кандидата перед переключением, подозрение на зависание |
| Проверка назначения | Доступность нужного сервиса, DNS, при необходимости UDP | Группы/правила с конкретными требованиями |
| Длительная проверка | Устойчивость передачи и прикладной сессии | Лаборатория и ручной тест; не каждый фоновый цикл |

TCP-connect служит дополнительной диагностикой. Его отказ не является универсальной причиной пропускать тест через ядро, особенно для UDP-протоколов.

Для проверки данных начать с 64–256 КиБ, общего deadline и ограничения фактически прочитанных байт, даже если сервер игнорирует Range. Использовать небольшие известные объекты/контролируемые endpoints, валидировать статус, TLS, длину и ожидаемый ответ; не принять страницу авторизации или заглушку за успех. Разделить холодную и повторную задержку. Сбой тела ответа сохранять как ошибку передачи.

Профиль проверки содержит несколько независимых целей и явный критерий успеха. Для универсального доступа стартовая гипотеза — успешные проверки двух независимых целей из трёх. Для конкретного сервиса его собственная проверка обязательна; общая доступность не заменяет её. Таймаут, лимитирование сервиса, запрет по региону и отказ прокси — разные результаты.

Доступность Telegram Web/API не доказывает работоспособность MTProto, медиа и звонков. UDP и DNS проверять отдельно, если они нужны маршруту. Нельзя объявлять сервер универсально рабочим по одному favicon.

Сначала переиспользовать пакетные тесты Keqdroid. Параллелизм адаптировать к устройству, ядру, сети и ограничениям подписки. Ограничить число одновременных попыток к одному хосту/аккаунту: лимиты провайдера могут создавать ложные отказы. Нужны отмена, очистка временных ядер и запрет применения результатов из старого поколения сети.

«Все подписки» означает общую область кандидатов. Полный скан выполняется по запросу и постепенно после значимых изменений. Фоновый режим поддерживает небольшой резерв и циклически проверяет остальной пул, не скачивая данные через все узлы каждые 30 секунд.

### 6а. Настраиваемые цели

[PROBE_PROFILES.md](PROBE_PROFILES.md) фиксирует обязательный свой URL, два начальных профиля (общий/контрольный) и расширение до сервисных групп. M1 реализует единый контракт метода, статуса, редиректов и тела; M3 выбирает глобальный узел по выбранному профилю; M4 связывает независимые профили с группами/маршрутами. Пользовательский контрольный URL не заменяется успехом нейтрального адреса, а Instagram не считается универсальным доказательством доступа к Telegram.

## 7. Автовыбор и переключение

### Допуск и оценка

Сначала применяются обязательные условия: включённая подписка, отсутствие исключения пользователем, совместимое ядро, ограничения маршрута/группы, транспорт и свежая проверка. Отключённый пользователем узел не становится резервом автоматически.

Затем оценивать подтверждённую долю успехов, недавние последовательные отказы, медианную задержку, устойчивый разброс, свежесть и достаточность наблюдений. Предпочесть робастную оценку разброса вместо единственного максимального выброса. Пропущенная проверка и отмена не являются отказом. Скорость использовать для подтверждения минимальной пригодности и устойчивого улучшения; разовый пик не должен перевешивать историю сбоев.

Не фиксировать произвольную формулу как доказанную. Сначала сравнить нынешнюю оценку Keqdroid с несколькими вариантами на одинаковых записанных сценариях. Новый узел с одним удачным тестом не должен автоматически вытеснять проверенный стабильный узел; ему нужны дополнительные наблюдения.

### Два независимых основания перехода

1. **Восстановление:** текущий путь действительно перестал выполнять требуемую работу, резерв проверен в текущей сети. Не ждать планового интервала улучшения.
2. **Улучшение:** текущий путь работает, но другой устойчиво существенно лучше. Такой переход разрешён только при подтверждённой выгоде и низкой цене разрыва сессий.

Стартовые параметры ниже — гипотезы для испытаний, а не обещанные оптимальные значения:

| Параметр | Стартовая настройка |
|---|---|
| Контроль активного пути | Около 30 секунд при активности, 60–120 секунд при простое; пробуждение по сетевому событию |
| Подтверждение обычного отказа | Два неуспешных раунда с независимыми целями; смерть процесса ядра обрабатывается отдельно |
| Готовый резерв | 2–3 узла, по возможности разные хосты/подписки |
| Проверка ради улучшения | Раз в 5–10 минут, небольшое число кандидатов |
| Порог по задержке | Одновременно ≥30% и ≥100 мс по сравнимой медиане; надёжность не хуже |
| Подтверждение улучшения | Три последовательных сопоставимых раунда |
| Удержание рабочего сервера | Не менее 10 минут для добровольного улучшения |
| Защита от колебаний | Не более двух добровольных переходов в час; при повторных авариях отдельный backoff |

При долгом звонке/загрузке добровольное улучшение откладывать, если сессию можно достоверно определить. Если ядро не даёт нужной информации — использовать консервативную политику и явную настройку. Наличие RX от одной сессии не доказывает исправность всех маршрутов; отсутствие трафика в простое не является отказом.

Отсутствие ответов от всех кандидатов означает «причина не установлена»: это может быть сеть, DNS, общий провайдер или сама тестовая цель. Приостанавливать штрафы отдельным узлам и проверять независимые контрольные сигналы. После восстановления сети отменять старые проверки и проверять текущий путь заново.

Переход: подготовить и проверить кандидат → применить конфиг → проверить уже действующий путь → подтвердить либо откатить, если прежний путь ещё пригоден. Одновременно выполняется только один переход. Пользовательский выбор отменяет незавершённую автоматическую операцию.

Не обещать бесшовность: перезапуск ядра и смена выхода могут оборвать TCP/UDP-сессии. Сохранение TUN само по себе не сохраняет соединения. Подготовка второго ядра возможна только при допустимых ресурсах и ограничениях аккаунта; при отсутствии hot switch измерять реальное время разрыва.

Видимые состояния: «работает», «проверяем соединение», «ищем резерв», «нет доступа к сети», «переключаем», «частичный доступ». Журнал объясняет переход: причина, старый/новый путь, подтверждающие результаты, время восстановления. Секреты в журнал не попадают.

## 8. Группы и маршрутизация

Группа — объект со стабильным ID, фильтром участников и собственной политикой выбора. Поддержать ручной набор и динамические условия: подписка, метка режима, подтверждённая пригодность, страна выхода, слова/теги. В первой версии фильтров предпочесть простые правила вместо произвольных затратных regex. Циклические вложения групп запрещены.

Страна узла различает три значения: метка имени, география адреса сервера и проверенная страна выхода. Для цепочки существенна последняя ступень. CDN, балансировка и неоднозначная GeoIP-база требуют статуса «неизвестно»; не угадывать страну по флагу в имени.

Расширить цель маршрута: direct, block, конкретный сервер, Auto-группа, цепочка. Условия — нынешние домены/IP/приложения/протоколы/порты плюс режим сети. Примеры: Telegram → группа с нужными транспортными проверками; иностранные сайты → общая устойчивая группа; выбранные RU-сервисы при БС → проверенная цепочка с нужным выходом.

Это явные правила с подбором внутри группы. Приложение не должно обещать автоматическое понимание требований каждого сайта. Для одновременных разных выходов нужен граф outbound в одном совместимом ядре либо проверенная композиция исполнителей. Независимые группы, требующие разных ядер, нельзя молча свести к одному глобальному серверу.

Оставить порядок правил Keqdroid v0.36.1 в совместимом режиме, включая пользовательское поле `order` в разделе всех приложений. Новые правила без позиции сохраняют предусмотренную upstream логику вставки. Новый управляемый режим компилирует явный порядок: обязательные ограничения → пользовательские блокировки → специфичные правила приложений/сервисов → общие пользовательские правила → разрешённые правила провайдера → fallback. Порядок отображается до применения; конфликтующие правила не меняются молча при миграции.

Провайдерский исходник хранится отдельно от пользовательских переопределений. Можно просмотреть происхождение и итог правила, отключить, переопределить действие, увидеть diff обновления. Изменения провайдера не стирают пользовательские overrides; неоднозначное сопоставление требует отображения конфликта. Технические DNS/bootstrap-правила выделить отдельно.

DNS должен следовать выбранному назначению. Bootstrap адреса самого прокси не должен зависеть от ещё не поднятого прокси. Для каждого правила задаётся поведение при недоступности цели: другой разрешённый путь или блокировка. Запрещён незаметный выход напрямую, особенно для Tailnet и защищённых маршрутов.

Hosts-списки: переиспользовать парсер и обновление Keqdroid, добавить статус загрузки, сроки, лимиты размера/числа доменов, ETag при поддержке сервера, последнюю рабочую версию, откат и разрешающие исключения. При ошибке загрузки сохранять рабочую базу. StevenBlack — источник доменной фильтрации, а не фильтр элементов веб-страницы. Не включать несколько огромных списков без оценки памяти.

## 9. Цепочки

Расширить существующую модель: каждая ступень ссылается на сервер либо группу. Для первого выпуска динамических цепочек достаточно двух ступеней. Уже существующие статические цепочки Keqdroid не сокращать: их совместимость должна сохраняться.

Выбирается **пара/путь**, а не независимо лучший сервер каждой группы. Доступность выхода проверяется через конкретный вход; задержка ступеней отдельно не равна характеристикам цепочки. Кешировать пригодность комбинации с учётом сети и версий конфигурации. Ограничить перебор, например тремя входами и тремя выходами, затем адаптировать по результатам.

Проверять совместимость TCP/UDP, адресацию, DNS, отсутствие повторов и циклов, достижимость следующего узла через предыдущий. При отказе ступени проверить новый полный путь. Переход на одиночный узел допускается только как заранее указанная политика.

Доступ к RU-сайту при БС зависит от доступности входа и возможности выхода связаться с сайтом. Группа с названием «RU» не создаёт такую возможность сама. Критерий приёмки — загрузка целевого сервиса через цепочку с ожидаемым выходом.

## 10. Рабочий профиль и защита

RKNHardering использовать как каталог проверок, а не как универсальный норматив безопасности. Видимость VPN, утечка трафика и доступ к управлению — разные проблемы [S9–S12].

Первый слой работ: аудит импортированных конфигураций, закрытых управляющих API и локальных listener; аутентификация оставшихся listener; минимизация экспортированных Android-компонентов; защита токенов/backup; отсутствие секретов в логах; проверка DNS/IPv6/UDP и маршрута при переключении. Сохранять существующую проверку подписей обновлений и происхождение зависимостей.

Не ставить MTU 1500 только ради прохождения детектора: это может ухудшить соединение. Проверять PMTU/MSS и реальные крупные передачи. Не выключать проверку сертификатов ради «починки пинга».

Пункт про рабочий профиль разделить на: (а) трафик, реально попавший в TUN; (б) доступ к адресу шлюза/локальному SOCKS или API; (в) системную видимость VPN. У IP-пакета TUN нет поля UID. На Android 10+ `getConnectionOwnerUid` ограничен TCP/UDP и видимостью вызывающего VPN, может вернуть неизвестного владельца [S8]. Поэтому обещание «любой пакет чужого профиля автоматически отбрасывается по UID» требует экспериментального подтверждения.

В Keqdroid v0.36.0 уже есть ConnectionOwnerServer, патчи Xray/mihomo и правила owner guard. Защита выбирается для Android TUN со split routing, но не allProxy; есть исключения для системного DNS и разрешающее поведение при некоторых ошибках lookup. Это требует проверки, особенно из соседнего профиля. Полный аудит и контракт строгого режима: [SECURITY_ISOLATION.md](SECURITY_ISOLATION.md). Наличие патча не заменяет проверки бинарника и реальной передачи.

R1 переносится в M0–M1: проверить основной/рабочий профиль, оба ядра, allProxy/include/exclude, DNS, UDP, IPv6, отказ owner service и повторное использование потоков. Исправлять подтверждённые пробелы, переиспользуя существующий механизм. API определения владельца доступен только для TCP/UDP; для остальных протоколов нужна отдельная политика. В строгом режиме ошибка проверки не должна молча разрешать передачу. Совместимость DNS, PMTU и входящих Tailnet-соединений проверяется отдельно.

Обычный APK не может гарантированно скрыть TUN и `TRANSPORT_VPN` от всех других приложений. Root/системные вмешательства не входят в базовый клиент. Приёмка защиты — устранённые конкретные несанкционированные пути и утечки, а не обещание «VPN не обнаруживается».

## 11. Tailscale и AmnesiaWG

Tailnet нужен не только для доступа к домашней сети, но и для синхронизации устройств. Поэтому минимальный прототип R2a переносится в раннюю фазу M1–M3; полный набор функций остаётся отдельной подсистемой. Android допускает один активный VPN-сервис на пользователя/профиль [S7]; запуск отдельных Tailscale и Orrdroid одновременно в одном профиле не является интеграцией.

Исследуемая архитектура: один VpnService Orrdroid, общий диспетчер маршрутов, встроенный адаптер Tailscale userspace/netstack. Для обмена настройками между приложениями Tailscale userspace может обслуживать собственные соединения без перехвата всего системного трафика; это меньший объём, чем полный Tailnet VPN. `tsnet` — кандидат для прототипа, но готовую мобильную интеграцию необходимо проверить [S13].

**Основной кандидат для R2b — готовый форк LiuTangLei.** Указанный пользователем `tailscale-awg-installer` содержит установщики и документацию; реализация находится в `LiuTangLei/tailscale`, мобильная оболочка — в `LiuTangLei/tailscale-android`. Проверен релиз v1.104.4; его дерево содержит AWG-настройки/LocalAPI и зависимость `LiuTangLei/wireguard-go`. В проверенном `main` нужные файлы отсутствовали, поэтому аудит и сборку вести по конкретному release tag/commit, а не по имени default branch [S16].

Форк документирует стандартный WireGuard, AWG v2/v3 и QUIC. В AWG должны совпадать необходимые общие параметры peers; часть параметров сохраняет обычную WireGuard-совместимость, часть меняет формат пакетов. Совместимость с control plane Tailscale/Headscale не доказывает связь с немодифицированными peers в любом AWG-режиме. QUIC — отдельная возможность; в первую версию Orrdroid её не включать без самостоятельного обоснования и тестов. Обнаружение готового кода уменьшает объём реализации, но не доказывает его стабильность на устройствах пользователя.

Внешний AWG-транспорт до собственного шлюза оставить запасной архитектурой. Для него переиспользуется поддержка AWG в Keqdroid/mihomo, проверяются маршруты control/DERP/direct peers, DNS, UDP, MTU и рекурсия. Не смешивать этот вариант с нативным AWG-транспортом форка Tailscale: у них разные зависимости и требования к peers.

В Karing v1.2.26.2925 подтверждены `SettingConfigItemUITailscale.authKey`, экран ввода Auth key и `SingboxOutboundTailscaleOptions` [S17]. Использовать как пример UX и интеграции с общим VPN. Перенос sing-box-обвязки в Xray/mihomo не является прямой заменой файла. Auth key служит регистрации устройства в Tailnet, а не подписью общих настроек и не готовым протоколом синхронизации. Не переносить один node state/private key между устройствами.

В ТЗ указано 1.5+; официальная документация уже описывает более новые версии AWG [S14]. При реализации выбрать конкретные совместимые версии клиента и сервера и тестировать согласованные параметры, а не обещать любую комбинацию 1.5+.

Разделить проверяемые уровни:

1. Доступ к адресам Tailnet и MagicDNS, авторизация, сохранение ключей, переподключение, соблюдение ACL/grants.
2. Subnet routes, выбор exit node, конфликт маршрутов и DNS, различение direct/DERP.
3. AWG как внешний транспорт; отказ AWG не должен открывать запрещённый прямой путь.
4. Матрица остальных функций официального Android-приложения: вход/выход, аккаунты, sharing/Taildrop и прочее — отдельная инвентаризация по зафиксированной версии. Каждая функция имеет статус «поддерживается / планируется / не поддерживается».

R2a завершается обменом подписанной тестовой конфигурацией между встроенными Tailnet-узлами двух устройств при работающем прокси. R2b отдельно проверяет общий TUN, TCP/UDP к Tailnet и транспорт AWG между совместимыми peers, включая DERP и смешанную сеть. По результатам выбирается адаптер и уточняется M6. Полный функциональный паритет не считается выполненным по факту успешного подключения.

## 11а. Синхронизация между устройствами

[SYNC.md](SYNC.md) задаёт два режима: защищённое главное устройство либо изменения от всех авторизованных устройств. В первом ведомые не могут переписать главное. Во втором объединяются операции/поля со стабильными ID, причинным порядком, конфликтами и tombstone; mtime файла не определяет победителя. Смена режима/ролей требует явной процедуры владельца и новой эпохи.

Оба режима используют единый защищённый формат поверх Tailnet, LAN или файла; WebDAV/Nextcloud и другие сервисы — отдельные адаптеры. Протокол шифрует данные до помещения во внешнее хранилище. Автоматический refresh провайдера отделяется от пользовательских правок, а параметры Auto и маршруты — от локальных измерений/интерфейсов/ключей устройств.

M3S-A: главное/ведомые, LAN и backup; M3S-B: multi-writer, офлайн и конфликты; M3S-C: хранилища. R2a добавляет Tailnet и не блокирует LAN-прототип. Зависимость всех этапов — миграции и проверка конфигурации M0/M1. Android TV/Google TV и desktop требуют своих проверок; синхронизация не создаёт отсутствующие сборки для иных ОС.

## 11б. Раздача SOCKS5/HTTP в LAN

[LAN_PROXY.md](LAN_PROXY.md): отдельное включение на выбранном LAN-интерфейсе, обязательные логин/пароль, ссылка и QR. Анонимный доступ запрещён. Выбор текущего пути/группы/цепочки, локальный DNS-контракт и ограничение ресурсов. Синхронизация не включает listener на другом устройстве. Control API и sync endpoint не публикуются вместе с прокси.

Прикладной LAN inbound отделён от TUN и существующей UID-защиты; её нельзя отключать ради раздачи. Поддержка SOCKS5 UDP/IPv6 и Android hotspot проверяется отдельно. Обычные SOCKS5/HTTP credentials не дают шифрования канала; для недоверенной сети предусмотрен Tailnet/совместимый защищённый транспорт.

## 12. Этапы, зависимости и ориентиры трудозатрат

Оценки предварительные, для разработчика с опытом Flutter, Android VPN и Go при доступном стенде. Это человеко-недели, не обещанные календарные даты. Уточнить после M0; не начинать отсчёт готовности продукта от момента написания плана.

| Этап | Результат и условие завершения | Оценка |
|---|---|---|
| M0. База и измерения | Импорт истории upstream, сборка без изменений, версии ядер, тестовый стенд, базовые метрики, миграционный контракт | 1–2 недели |
| M1. Проверки и данные | Структурированный результат, проверка тела, история по сети, отмена/лимиты; тест заголовки-есть/тело-зависло проходит | 2–3 |
| M2. Режим сети | Авто/ручной режим, независимые цели, неизвестно/offline/portal, отсутствие колебаний | 1–2 |
| M3. Глобальный Auto | Все подписки, авария/улучшение, резерв, фильтр списка, фон, журнал, полевые испытания | 3–5 |
| M4. Группы и правила | Группы как цели, DNS, overrides провайдера, пресеты/hosts, объяснение маршрута | 3–5 |
| M5. Цепочки и изоляция | Двухступенчатые группы, проверка пути, реализуемая часть R1, регрессия утечек | 3–5 |
| R1. Аудит изоляции | Проверка имеющихся owner guard, allProxy и DNS; границы строгого режима | 1–2 на аудит в M0–M1; исправления оценить по результатам |
| R2a. Минимальный Tailnet | Встроенный обмен настройками при работающем прокси; ранний этап, до M3S | 1–2 |
| M3S-A. Базовая синхронизация | Главное/ведомые, подпись, LAN/backup, атомарность и профили | Прежние 3–5 требуют уточнения для новых транспортов |
| M3S-B. Все устройства | Журнал операций, слияние, конфликты, удаления, отзыв и смена режима | Оценить после прототипа; не входит в старые 3–5 |
| M3S-C. Хранилища | WebDAV, затем выбранные адаптеры и их семантика записи | Отдельная оценка по адаптеру |
| M3P. LAN-прокси | SOCKS5/HTTP с авторизацией, URI/QR и изоляцией | Оценить после проверки адаптеров ядер |
| R2b. Tailnet/AWG-прототип | Аудит и пробная интеграция LiuTangLei, выбор архитектуры M6 | 2–4 |
| M6. Tailnet | Реализация только подтверждённой архитектуры и согласованного набора функций | Оценить после R2; предварительно ещё 6–12+ |

M0–M3: ориентир 7–12 человеко-недель плюс календарное время длительных полевых прогонов. Основной продукт до M5: примерно 13–22 человеко-недели без R1, синхронизации и полного паритета Tailscale. Прежняя оценка R2a + M3S в 4–7 человеко-недель относилась только к модели главного через Tailnet. Она не покрывает новые M3S-B/C и M3P; общий объём пересчитать после прототипов. R2b/M6 оцениваются отдельно; наличие готового форка требует пересчёта после аудита, не сохранения старой оценки «написать AWG с нуля». Для небольшой команды задачи частично параллельны, но сетевой исполнитель и приёмка остаются общими зависимостями.

## 13. Репозиторий, версии и первый backlog

Основной репозиторий: `orrtyom/orrdroid`. Сейчас он содержит документацию проектирования; он не является уже импортированной копией исходников Keqdroid.

Первый технический этап — импортировать выбранный upstream commit **с историей**, сохранить авторство/лицензионные файлы и связать его с историей планирования обычным merge. Не заменять upstream случайным ZIP и не переписывать уже опубликованную историю. При конфликте README сохранить upstream-документацию отдельно, оставив индекс Orrdroid. Подключить upstream remote, вести учёт заимствований и совместимости лицензий до переноса кода сторонних проектов.

Разработка: короткие `feat/*`, `fix/*`, `docs/*`; изменения через небольшие PR с причиной, проверками и ограничениями. В `main` — прошедшие проверки изменения. Для обновлений upstream — отдельная интеграционная ветка и регрессионный прогон. Общие улучшения оформлять так, чтобы их можно было предложить оригинальному проекту независимо от интерфейса Orrdroid.

Версии Orrdroid независимы от Keqdroid: `v0.1.0-alpha.1` после первого пригодного M3-прототипа, beta после выполнения базовой приёмки, стабильная версия после полевого сравнения. Это планируемые имена: сейчас теги и APK не выпускаются. В каждом выпуске фиксировать upstream SHA, версии ядер, схему backup, Android versionCode, список миграций и известные ограничения.

Отдельные package ID и ключ подписи позволяют поставить Orrdroid рядом с Keqdroid. Секрет подписи хранится вне репозитория. Импорт старого backup выполняется в копию; downgrade не должен читать новую схему как старую. Реальные подписки, ключи, UUID, endpoint пользователя и сырые диагностические журналы не коммитить; использовать синтетические fixtures.
