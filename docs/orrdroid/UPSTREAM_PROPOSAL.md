# Черновик issue для Keqdroid — полное техническое задание

Статус — сохранён для ручной отправки владельцем Orrdroid. Issue в upstream не создан. Проверка исходных возможностей проведена 12 ноября 2026 по Keqdroid v0.36.3, Karing v1.2.26.2929 и Farvater v1.0.31. Черновик охватывает всё ТЗ Orrdroid, включая дальнейшие этапы. Первый этап определяет очередность, а не границу предложения.

**Предлагаемый заголовок**

Развитие Keqdroid: БС/ЧС, Auto-группы и цепочки, сервисные проверки, синхронизация, LAN и Tailnet/AWG

**Текст issue**

Здравствуйте! Предлагаю обсудить полный набор улучшений Keqdroid, собранный в техническом задании проекта [Orrdroid](https://github.com/orrtyom/orrdroid): режимы сети и маршрутизацию, проверки и автовыбор, группы и цепочки, синхронизацию устройств, LAN-прокси, встроенный Tailnet/AWG и защиту Android VPN. Ниже описан весь целевой функционал, с приоритетным первым этапом и последующей последовательностью реализации. Каждое направление можно разрабатывать и принимать отдельными изменениями.

Основной сценарий — у пользователя несколько подписок, обычная сеть сменяется мобильными белыми списками, а отдельные сервисы требуют российского либо зарубежного выхода. Нужно сохранить заданные маршруты и ручной выбор, находить рабочий резерв среди разрешённых подписок и различать успешный короткий ответ от передачи данных.

БС означает режим белых списков сети, ЧС — режим выборочных блокировок и замедлений. Это условие маршрута, отдельное от списка назначений и подписки узлов.

Предложение основано на чтении кода v0.36.3. Сравнительные испытания приложений на одинаковом стенде ещё не проводились.

## Что уже есть и что предлагается расширить

| Возможность Keqdroid | Предлагаемое расширение |
|---|---|
| Свой HTTPS URL, пинг всех серверов/подписки/цепочек | Сохранить настройку и пакетные проверки, добавить отдельный результат проверки тела и передачи |
| DIRECT / BLOCK / текущий / отдельный сервер, порядок правил | Добавить условие «Когда» и пресет «Заблокировано для РФ» |

В v0.36.3 уже исправлена авторизация запросов приложения через локальный proxy. Это исправление относится к внутреннему proxy и сохраняется независимо от предложения по LAN.

## 1. Условные маршруты

Расширить редактор до «Кто → Что → Когда → Куда».

- В «Что» добавить «Заблокировано для РФ» для сервисов, ограничивающих доступ из России или с российских IP. Источник должен содержать проверенные назначения, область ограничения и дату обновления.
- В «Когда» добавить «Всегда / БС / ЧС». Старые правила при миграции получают «Всегда».
- В «Куда» явно показывать сохранённые цепочки, совместимые с mihomo. Ссылаться на стабильный ID, валидировать все ступени и показывать причину несовместимости.
- После переключения режима пересобрать правила и DNS и применить через существующее переподключение.
- Если правило не совпало, в ЧС использовать DIRECT, в БС — текущий сервер. Для совпавшего правила с обязательной цепочкой/географией при отказе использовать только явно заданный допустимый резерв либо BLOCK.
- Предусмотреть пользовательские шаблоны порядка правил, без автоматического создания сервисных профилей после установки.

Шаблон БС сначала отправляет мобильный белый список напрямую, затем российские назначения по geosite **или** geoip через подтверждённый выход РФ, остальное через текущий сервер. В шаблоне ЧС сервисы «Заблокировано для РФ» идут через подтверждённый выход вне РФ, затем блокировки/замедления РКН через выбранный proxy, остальное напрямую. При пересечении списков требование выхода вне РФ сохраняется. Пользователь видит порядок до применения и назначает выходы сам.

Список «Заблокировано для РФ» отличается от `ru-available-only-inside`, которому нужен российский выход. Исходный [справочный список Orrdroid](https://github.com/orrtyom/orrdroid/blob/main/docs/orrdroid/sources/russia-geoblocked-services.txt) ещё требует нормализации в домены/IP. Ограничения аккаунтов и отдельных функций не всегда решаются сменой IP.

Для страны выхода использовать существующий Cloudflare trace, расширив проверку до конкретного сервера/целой цепочки. География берётся по фактическому выходу последней ступени. Неизвестная страна остаётся неизвестной.

Точки расширения уже есть в [TrafficRoute](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/models/traffic_route.dart), [route_servers.dart](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/utils/route_servers.dart), [routing_presets.dart](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/utils/routing_presets.dart) и [exit_ip_service.dart](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/services/exit_ip_service.dart). Статические цепочки как основной выход уже доступны и на совместимом Xray. Предлагаемый первый шаг касается отдельной цели маршрута через mihomo.

## 2. Первый запуск и определение БС/ЧС

В Orrdroid планируется перенос полного сценария Farvater v1.0.31 в рамках первого запуска, загрузки источников и определения режима. Для Keqdroid предлагается обсудить такую же опциональную функцию.

В Farvater прямые внешние HTTPS GET-пробы со статусом 2xx и минимум 32 КиБ определяют ЧС. Если они не прошли, любой HTTP-ответ российских HEAD-целей определяет БС. При отсутствии обоих результатов возвращается неизвестное состояние. При неизвестном режиме чистой установки действуют только правила «Всегда» и штатное действие «Всё остальное» выбранного профиля. Ручной режим имеет приоритет. Последний известный режим сохраняется, а при чистой установке и неизвестном режиме допускаются все разрешённые источники.

Нужна интеграция всего сценария с загрузкой подписок и кэшем, выбором первого узла, сменой физической сети и восстановлением VPN. Проверки режима должны идти через физическую сеть. Результаты старой сети отменяются. Подписки при поднятом VPN используют рабочие credentials локального proxy. Восстановление сохранённой сессии Keqdroid сохраняется, явное отключение пользователем не отменяется автоматикой.

Для переноса зафиксировать параметры Farvater: параллельные внешние цели Google/Cloudflare/GitHub, затем российские Яндекс/VK/Госуслуги; Range на 64 КиБ, без редиректов и автоматического повтора, connect/read timeout по 4 секунды и общий call timeout 8 секунд. Список целей и параметры должны иметь версию. Неопределённость, отсутствие физической сети и captive portal показываются раздельно, если причина подтверждена; не угадывать причину по единственному таймауту.

До подключения использовать доступный обычный HTTP-путь, после подключения — локальный proxy; сохранить перебор URL источника и поддерживаемых представлений, последнюю рабочую копию и локальный импорт при отсутствии начального доступа. Подписки и узлы добавляются пользователем. Для подключения брать выбранный узел, иначе лучший известный или доступный первый; ранее нерабочий узел перепроверять. Перенести сценарий поиска «Галс» с проверкой физической сети и фактической передачи через кандидата. Пустой список предлагает импорт. Запрет прямых проб пользователем сохраняется: при нём доступны ручной режим либо неизвестный результат.

В исходном Farvater есть интервалы повторных попыток и защиты от частых смен. Их нужно согласовать с контроллером Keqdroid. Поведение в фоне/Doze проверяется отдельно.

Источники — [NetModeDetector](https://github.com/farvater-app/farvater/blob/v1.0.31/app/src/main/java/app/farvater/engine/NetModeDetector.kt), [MainViewModel](https://github.com/farvater-app/farvater/blob/v1.0.31/app/src/main/java/app/farvater/ui/MainViewModel.kt), [ModeSwitch](https://github.com/farvater-app/farvater/blob/v1.0.31/app/src/main/java/app/farvater/engine/ModeSwitch.kt). При переносе кода сохраняются авторство и применимые лицензионные условия.

## 3. GlobalAuto и состояния серверов

Добавить выбираемую область Auto — текущая подписка, выбранные подписки или все разрешённые подписки. Использовать существующие историю и watchdog.

Допуск учитывает исключения пользователя, режим, совместимость ядра, обязательную страну выхода и ограничения провайдеров. Поддерживать небольшой проверенный резерв из разных источников. Полный пул обходить постепенно с ограничением параллелизма и трафика.

В `AutoServerSelect.eligible()` сейчас при отсутствии неотмеченных узлов возвращается вся подписка. Для новой области GlobalAuto предлагается строго соблюдать исключения: пустой допустимый пул даёт «нет допустимых кандидатов», а не повторное включение исключённых узлов. Поведение прежнего Auto при миграции должно быть явно согласовано и объяснено пользователю.

Базовые исключения уже обсуждались в закрытом как выполненный [issue #15](https://github.com/Lemonochka/keqdroid/issues/15). Предложение выше касается расширения на общий пул и поведения при его исчерпании.

Ручной выбор сохраняется до явного возврата в Auto. Обновление подписки и смена выбранного сервера сохраняют пользовательские правила. Отмена проверки и результат прежней сети не считаются отказом. Массовый сбой тестовой цели не должен запускать бесконечный перебор серверов.

Фильтр «Скрыть не прошедшие проверку» сделать опциональным. Непроверенные, устаревшие и подтверждённо не прошедшие узлы различаются. Скрытие не удаляет узел и не прекращает повторные проверки.

Текущая база — [auto_server_select.dart](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/services/auto_server_select.dart). Karing показывает подход к [URLTest-группам с узлами включённых источников](https://github.com/KaringX/karing/blob/v1.2.26.2929/lib/screens/urltest_group_custom_screen.dart). Независимый Auto для каждого маршрута входит в полный объём предложения и реализуется следующим этапом по §6.

## 4. Отдельное подтверждение передачи данных

В Android-функции [httpProbeViaSocks](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/android/app/src/main/kotlin/com/keqdroid/keqdroid/EphemeralXrayPing.kt) время измеряется до заголовков, а чтение тела выполняется в `runCatching`. Ошибка тела может не изменить успешный результат. Отдельная проверка скорости уже есть.

Предлагается общий для Xray/mihomo результат с HTTP-кодом, числом байт, временем ответа, временем передачи и причиной ошибки. Для ограниченного GET задать общий deadline и предел реально прочитанных байт, даже если цель игнорирует Range. Проверять ожидаемый ответ и отличать DNS/TLS/timeout/429/неверное тело от общего отказа узла.

В результате хранить ID узла/полного пути, hash существенной конфигурации, ядро и версию, поколение физической сети, профиль и версию цели, метод и время. Смена credentials, транспорта, ядра, сети или критериев проверки инвалидирует старый допуск; переименование узла — нет. Пробы идут строго через проверяемый путь с его DNS, без подмены текущим GlobalAuto и без direct fallback. Bootstrap DNS адреса самого proxy рассматривается отдельно. TCP-connect — дополнительная диагностика, его отказ не исключает UDP-протоколы из проверки через ядро.

Разделить время до заголовков, дочитывание тела, холодный замер и повтор с keep-alive. Для favicon/файла проверять ожидаемый код, формат и завершённость ответа; HTML авторизации не считать успехом картинки. Ограничить редиректы и допустимые конечные домены. 403/429/5xx и ответ с неверным телом могут подтверждать работающий транспорт, но не сервисный допуск. Ожидаемый 401 допустим только для специально описанной цели. Начальный диапазон объёмной проверки 64–256 КиБ — параметр для испытаний; длительные TCP/UDP-сессии проверяются отдельно. Не отправлять cookies, токены аккаунтов или пользовательские данные в фоновых пробах; не менять сторонний URL произвольными query-параметрами.

Сохранить штатный HTTPS URL и пользовательское значение. Ожидаемый 204 остаётся успешной быстрой проверкой без тела. Передача объёма проверяется отдельным объектом. Нейтральная цель не заменяет обязательную пользовательскую сервисную проверку. После чистой установки используется обычная цель Keqdis, пользователь сам выбирает нужные URL и правила.

## 5. LAN-прокси с реквизитами, ссылкой и QR

В [настройках LAN](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/screens/settings/lan_sharing.dart) уже есть SOCKS5/HTTP и поля реквизитов. Сейчас копируется адрес с портом, а генераторы допускают анонимный LAN при пустых реквизитах.

Предлагается требовать непустые логин и пароль при включении раздачи, генерировать пароль при первом включении и проверять условие одновременно в UI, [Xray](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/utils/config_gen.dart) и [mihomo](https://github.com/Lemonochka/keqdroid/blob/v0.36.3/lib/utils/mihomo_config_gen.dart). Старую включённую раздачу без реквизитов при миграции остановить до настройки.

Добавить копирование `socks5://user:password@host:port` / `http://user:password@host:port` и QR с тем же URI. Кодировать специальные символы, учитывать IPv6 и смену LAN-адреса. Показывать пароль/QR по действию пользователя. Внутренний proxy и управляющее API сохраняют собственные реквизиты и границы доступа.

Полный LAN-функционал включает отдельное локальное включение, выбор интерфейса/адреса и портов, текущего VPN/Auto, группы или целой цепочки как назначения. SOCKS5 CONNECT, HTTP forward и CONNECT обязательны; UDP ASSOCIATE, remote DNS, IPv6, Android hotspot и изоляция Wi-Fi-клиентов проверяются по ядрам/платформам. Неподдерживаемый вариант даёт явную ошибку. Прикладной proxy не означает раздачу всего IP-трафика hotspot без настройки клиентов.

LAN-вход получает отдельный inbound tag и DNS/маршрутную политику; UID приложений телефона не описывает приложения удалённого клиента. Bind и допустимые подсети не расширяются автоматически на мобильный/публичный интерфейс, IPv6 соблюдает те же ограничения. При смене сети обновлять адрес/QR или останавливать доступ. Не ослаблять owner guard TUN ради LAN. Падение ядра, пустая группа и смена пути не включают скрытый direct fallback; обрыв существующих сессий показывается честно.

Экран показывает статус, протокол, адрес, порт, логин, скрытый пароль, назначение и число соединений; предоставляет ручные поля, показ/смену пароля, ссылку, QR и отключение. Не все клиенты импортируют URI/QR: совместимость и remote DNS проверяются отдельно. Ограничить попытки авторизации, соединения, время и ресурсы. Смена пароля отзывает старые ссылки с явной политикой уже открытых сессий. Не выводить реквизиты в логи, общую диагностику или публичный веб-интерфейс; очищать clipboard, где возможно.

Включение, bind и пароль раздачи локальны; sync/обычный backup на другом устройстве не открывают listener и не клонируют его реквизиты. Автозапуск раздачи — отдельная локальная настройка. Control API, sync endpoint, debug и экспорт подписок не публикуются вместе с proxy; UPnP не включается. SOCKS5/HTTP-аутентификация сама по себе не шифрует канал: для недоверенной сети нужен Tailnet либо совместимый защищённый транспорт.

## 6. Независимые Auto-группы, сервисные профили и политика переключения

### Группы серверов

Добавить группы со стабильным ID, именем, ручным составом либо динамическим фильтром. Источники участников — все разрешённые подписки и ручные узлы. Условия: подписка, предполагаемый/определённый режим сети, подтверждённая страна фактического выхода, теги/ключевые слова, пригодность для выбранного профиля; готовые и пользовательские фильтры. Начать с простых предсказуемых условий, исключить циклические вложения.

Метка страны в названии, география IP сервера и страна фактического выхода — разные свойства. Не угадывать выход по флагу. При смене сети, пути или конфигурации подтверждение устаревает, а динамический состав пересчитывается. Обновление подписки сохраняет ID/ссылки и исключения; исчезнувший узел не заменяется другим с тем же именем молча.

У каждой используемой группы свои активный путь, проверенный резерв, профиль проверки, история и политика выбора. Группа становится целью маршрута. Отказ группы Telegram не должен менять исправный российский выход другого маршрута. Единый контроллер согласует изменения групп и исполнителя, исключая гонки с ручным выбором и обновлением конфигурации.

В mihomo проверить управление selector, в Xray — balancer/outbound API на фактически поставляемых версиях. Если отдельное переключение невозможно, явно показать необходимость переподключения и его последствия. Одновременно поддерживать несколько совместимых выходов в одном ядре; сохранение TUN само по себе не означает сохранения TCP/UDP-сессий.

### Профили проверок

Предусмотреть сохранённые профили «Общий доступ», «Telegram + Instagram / контрольный ресурс» и пользовательские сервисные профили. В каждой форме — пресет/свой HTTPS URL, метод, ожидаемый результат, кнопка проверки, последнее состояние и время. Выбранный профиль можно назначить GlobalAuto, группе или маршруту. Несколько URL имеют явную логику ANY/ALL; критерий «2 из 3 независимых целей» для общего доступа — отдельная настраиваемая гипотеза для испытаний.

Профили не создаются автоматически после чистой установки: сохраняется штатная цель Keqdis. По явному выбору пользователя Telegram и Instagram используют общую группу и Instagram URL, например `https://www.instagram.com/favicon.ico`; отдельная Telegram-проба для такого профиля не обязательна. Это пользовательская эвристика, а не доказательство работы MTProto, медиа и звонков. При выборе отдельной Telegram-проверки её результат учитывается самостоятельно, с разделением Web/API, протокола и медиа/UDP, если соответствующий тест реализован.

История и допуск независимы по профилю и пути. Успешный Google не компенсирует отказ обязательного Instagram URL. Непройденный профиль не делает узел нерабочим для всех других назначений. Российский выход исключается только явной географической политикой, а не названием сервисного профиля. Фоновый тест маленького объекта не подтверждает длительную передачу или полную работу приложения.

### Отказ и добровольное улучшение

После обязательного допуска ранжировать по доле успехов, последовательным недавним отказам, медианной задержке, робастному разбросу, свежести и достаточности наблюдений. Разовый пик скорости или один успешный замер нового узла не вытесняет проверенный стабильный путь. Формулу не объявлять оптимальной заранее: сравнить существующую оценку Keqdroid и варианты на одинаковых записанных сценариях. Скорость используется для минимальной пригодности и устойчивого улучшения.

Разделить два режима перехода:

- Аварийный — текущий путь перестал выполнять обязательные проверки; выбирается пригодный разрешённый резерв, без ожидания таймера улучшения.
- Добровольный — другой путь устойчиво лучше при не худшей надёжности; переход учитывает историю, разброс, стоимость обрыва и минимальное время удержания.

Настройки ниже — стартовые параметры для измерений, не гарантированно оптимальные значения:

| Параметр | Начальный ориентир |
|---|---|
| Контроль активного пути | Около 30 секунд при активности, 60–120 секунд в простое; запуск по сетевому событию |
| Подтверждение обычного отказа | Два неуспешных раунда с независимой диагностикой; смерть процесса ядра обрабатывается отдельно |
| Резерв | 2–3 проверенных пути, по возможности разные хосты/подписки |
| Поиск улучшения | Небольшой набор кандидатов раз в 5–10 минут |
| Улучшение задержки | Одновременно не менее 30% и 100 мс по сравнимой медиане, надёжность не хуже |
| Устойчивость улучшения | Три сопоставимых последовательных раунда |
| Удержание рабочего пути | Не менее 10 минут перед добровольной сменой |
| Защита от колебаний | Не более двух добровольных смен в час; отдельный backoff повторных аварий |

При звонке/длительной загрузке откладывать добровольное улучшение, если активную сессию можно достоверно определить; иначе применять консервативную политику и явную настройку. Отсутствие трафика в простое не является отказом, а RX старой сессии не доказывает доступность новых запросов.

Переключение выполняется последовательно: подготовка и проверка кандидата → применение → проверка действующего пути с правилами и DNS → подтверждение либо откат на ещё допустимый путь. Ручное действие отменяет незавершённую автоматическую операцию. Подготовка дополнительного проверочного ядра учитывает память, батарею и лимиты аккаунта.

Полный скан выполняется по запросу и постепенно после значимых обновлений. В фоне проверяются активные группы и небольшой резерв, остальной пул обходится по очереди. Лимитировать параллелизм, число временных ядер, байты, частоту запросов на домен/хост/аккаунт; соблюдать backoff после 429. Отмена, массовая ошибка цели и результат старой сети не штрафуют каждый узел как отдельный отказ.

Отказ обязательной цели не подменяется успехом нейтральной. При массовом сбое отмечать неподтверждённость профиля, диагностировать сеть/цель и не запускать бесконечные переключения. Все исключённые кандидаты остаются исключёнными даже при пустом пуле.

## 7. Полная маршрутизация, правила провайдеров и hosts

Сохранить существующие условия домен/IP/приложение/протокол/порт и расширить редактор «Кто → Что → Когда → Куда». Полный набор целей: DIRECT, BLOCK, текущий сервер, отдельный сервер, Auto-группа, статическая или динамическая цепочка. Одновременные правила могут использовать разные выходы. Условие БС/ЧС применяется вместе с остальными условиями.

Порядок правил Keqdroid уже существует; его нужно сохранить, включая пользовательские позиции. В управляемом варианте показывать итоговый приоритет до применения: обязательные ограничения → пользовательские блокировки → специфичные правила приложений/сервисов → общие пользовательские правила → разрешённые правила провайдера → «Всё остальное». При импорте не переставлять конфликтующие правила молча. Шаблоны БС/ЧС из §1 применяются только пользователем; более конкретное обязательное требование выхода не теряется при пересечении списков.

Добавить объяснение результата маршрутизации: какое правило совпало, откуда оно получено, почему выбран данный путь, какая проверка/страна подтверждена и что произойдёт при отказе. Привязки по ID переживают переименование, сортировку и обновление подписки. При смене Auto между подписками пользовательские маршруты и DNS не заменяются незаметно профилем нового провайдера.

Правила провайдера хранить отдельно от пользовательских переопределений. Предоставить просмотр отдельных правил, происхождения и итогового действия, отключение и редактирование/переопределение; показывать diff при обновлении. Пользовательские изменения переживают refresh. Неоднозначное сопоставление после обновления вызывает видимый конфликт, а не потерю правок. Технические bootstrap/DNS-правила выделяются отдельно.

Для списков назначений сохранить ru-whitelist, Re:filter и другие поддерживаемые источники; добавить «Заблокировано для РФ» с областью ограничения, датой и источником. Различать ограничения РКН, ограничения доступа из РФ/с российских IP и сервисы, доступные только внутри РФ. При наличии отдельных источников блокировок и замедлений хранить их отдельно; единичный медленный замер не превращается в автоматическое правило.

Переиспользовать hosts/AdBlock/списки по URL; поддержать пользовательские автообновляемые источники, включая StevenBlack, готовые пресеты и исключения. Показывать время/статус загрузки, ограничивать размер и число записей, использовать ETag при наличии, сохранять последнюю рабочую версию и откат при ошибке. Оценивать память больших наборов. Hosts фильтрует домены, а не элементы веб-страниц.

DNS следует назначенному пути; разрешение адреса самого proxy не зависит от ещё не поднятого proxy. Проверять TCP/UDP, IPv4/IPv6 и цепочки. Отказ обязательного выхода обрабатывается допустимым резервом либо BLOCK, отдельно от отсутствия совпадений. При смене режима закрывать потоки, чей прежний выход запрещён новой политикой; откат допускается только без нарушения новой политики. Применение к уже открытым сессиям и реальный разрыв измеряются.

## 8. Статические и динамические цепочки

Сохранить существующие статические цепочки Keqdroid и их совместимость. Полная модель допускает ступени «сервер → сервер», «сервер → группа», «группа → сервер» и «группа → группа». Каждая ступень ссылается на стабильный ID сервера/группы. Сохранённая цепочка выбирается в «Куда», имеет имя, явные требования к выходу и политику отказа. Начать динамические цепочки с двух ступеней, не сокращая имеющуюся поддержку статических.

Выбирать и проверять целый путь, а не независимо два лучших пинга. Выход должен быть достижим через вход; сумма отдельных задержек не заменяет проверку цепочки. Кэш пригодности комбинаций привязан к сети и версиям конфигураций. Ограничивать перебор, например исходным набором трёх входов и трёх выходов с дальнейшим адаптивным расширением.

Проверять совместимость всех ступеней с ядром, DNS, TCP/UDP, адресацию, отсутствие повторов и циклов, фактическую страну последней ступени и загрузку целевого сервиса. При отказе ступени проверяется новый полный путь. Переход с цепочки на одиночный сервер разрешён только заранее заданной политикой; название группы «RU» не подтверждает доступность российских сайтов в БС.

Отдельная цель статической цепочки сначала использует готовый адаптер mihomo. Расширение Xray требует собственного генератора нескольких выходов и проверки тегов/DNS/совместимости; основной совместимый выход-цепочка Xray уже есть. Это раздельные сценарии.

Для графа выходов разных ядер сначала показывать конфликт конфигурации. Возможная композиция Xray и mihomo через внутренний адаптер в одном VpnService — самостоятельное исследование: управление процессами, DNS/UDP, ресурсы, отказ и отсутствие рекурсии. Полный набор поддерживаемых цепочек фиксируется матрицей, а не обещанием любой комбинации протоколов.

## 9. Синхронизация настроек и подписок между устройствами

Целевой набор устройств — телефоны, планшеты, компьютеры и ТВ. Начать с Android↔Android, затем поддерживаемые desktop и Android TV/Google TV с собственной приёмкой. Синхронизация не создаёт автоматически отсутствующие сборки под другие ОС.

### Два обязательных режима

| Режим | Полномочия | Поведение офлайн |
|---|---|---|
| Главное устройство | Ровно один издатель подписывает общие ревизии; ведомые читают назначенный профиль и не могут переписать главное | Последняя проверенная конфигурация продолжает работать; новое главное автоматически не избирается |
| Все устройства | Каждый авторизованный участник с правом записи публикует свои изменения; возможны участники только для чтения | Локальные правки сохраняются и объединяются после восстановления связи |

Режим главного защищается на уровне протокола, а не только интерфейса. Ведомое не изменяет общий слой через запрос, облачный файл, импорт backup или поддельное «более новое» время. Ключ подписи главного не передаётся ведомым. Выход из группы или независимая локальная копия доступны явно, без отправки этой копии обратно. Отчёт о доставке не является правкой настроек.

В режиме всех устройств «последние изменения» применяются к объектам/полям. Правка подписки на телефоне и маршрута на компьютере сохраняются обе. Старый backup не заменяет весь новый документ по mtime или времени загрузки. Формат слияния закрепить после прототипа:

- Стабильные ID подписок, групп, правил и цепочек; operation ID, автор, эпоха группы, счётчик автора и причинный контекст. Повторная доставка идемпотентна.
- Правка после получения предыдущей версии заменяет её; причинный порядок важнее системных часов.
- Одновременные независимые правки одного поля сходятся детерминированно, например через LWW-регистр с гибридной меткой времени и ID автора. Обе версии остаются в журнале, проигравшую можно восстановить новой правкой. Это не гарантия физически последнего нажатия.
- Скачки часов, неверные счётчики и неизвестные эпохи вызывают конфликт/карантин. Пределы и формат времени фиксируются до реализации.
- Удаления сохраняются как tombstone. Долгий офлайн не воскрешает объекты; очистка возможна после подтверждённого checkpoint либо исключения старого устройства с новым bootstrap.
- Порядок маршрутов применяется атомарным версионируемым списком ID. Одновременные перестановки — конфликт, а не независимое сложение полей order.
- Ссылки на удалённые объекты, несовместимая конфигурация и конфликт секретов не применяются частично. Сохраняется последняя рабочая версия; автоматическое слияние не включает скрытый DIRECT.

Смена режима действует на всю группу и подтверждается владельцем отдельной процедурой с новой подписанной эпохой и правами. При переходе к главному явно выбрать издателя и исходный снимок; неприменённые правки сохранить для просмотра. При утрате главного использовать подготовленное восстановление либо повторное сопряжение. Роли, отзыв, ключи и режим не разрешаются обычным LWW-слиянием; ведомое не повышает себя самостоятельно.

### Общие данные и локальные настройки

| Данные | Политика |
|---|---|
| Подписки, URL и credentials | Зашифрованный профиль только назначенным участникам |
| Ручные узлы, AWG, группы, цепочки, маршруты и порядок, overrides, hosts | Декларативная конфигурация со стабильными ID |
| Политики Auto и сервисные профили | Общие параметры с явными профилями устройств |
| Узлы обновлённой подписки | Снимок с происхождением, base revision/hash; не смешивать две выдачи провайдера по отдельным узлам |
| Активный путь, ping/отказы, физический режим, DNS-кэш и резерв Auto | Локальные измерения, не навязываются другому устройству |
| Приложения/пути процессов | Платформенные привязки; неизвестное приложение не превращается в «все приложения» |
| MTU, интерфейсы, порты, UI, энергосбережение | Локальный слой либо явно назначенный профиль |
| Включение LAN, bind и пароль | Локально; sync не открывает раздачу на другом устройстве |
| Node state/private keys Tailscale, signing keys, keystore | Не клонировать в обычном backup/sync |
| Tailnet Auth key и токены хранилищ | Настройка канала при сопряжении, отдельно от общих подписок |

В режиме главного подписки обновляет главное. В режиме всех устройств ограничивать дублирующий refresh; выдачи с разными UA/HWID/платформой не смешиваются молча. Сохранять выбранный общий снимок либо platform overlay, спорные снимки показывать как конфликт. Refresh провайдера не считается пользовательской правкой URL или маршрутов. Учитывать лимиты аккаунтов и назначенные профили устройств.

### Каналы обмена

| Канал | Требования |
|---|---|
| Tailnet | Предпочтительный межсетевой транспорт; встроенный userspace при работающем VPN, отдельное сопряжение приложения |
| LAN | Защищённый sync endpoint на выбранном интерфейсе, TLS с закреплением ключа после QR/кода; ручной адрес обязателен, mDNS опционален |
| Шифрованный backup/файл | Офлайн-перенос, восстановление, preview/diff; импорт не обходит права главного |
| WebDAV/Nextcloud | Приоритетный внешний адаптер, клиентское шифрование и подписи, проверка конкурентных записей и повторов |
| S3-совместимое хранилище | Дополнительный адаптер после прототипа, отдельные credentials и неизменяемые объекты |
| Синхронизируемая папка, Drive/OneDrive и аналоги | Дополнительные выбранные адаптеры после проверки API, фоновых ограничений и конфликтных копий |

Оба режима используют один формат операций/снимков независимо от канала. Внешний сервис хранит зашифрованные данные без ключей расшифрования. Для нескольких авторов не использовать один перезаписываемый файл: нужны журналы/объекты по устройствам, manifest/checkpoint и проверка пропусков, дублей и rollback. Условная запись и атомарность WebDAV/S3 проверяются на конкретном сервисе. Несколько каналов не приводят к повторному применению операции.

Обычный backup без истории репликации импортируется с preview как новая локальная операция; на ведомом не заменяет управляемый слой. Восстановление и файловая синхронизация — разные действия. Tailnet-listener привязан к Tailnet; LAN-sync отдельно включается и не появляется автоматически вместе с SOCKS/HTTP.

### Сопряжение, применение и отзыв

QR/одноразовый код содержит ограниченные bootstrap-данные и pin ключа, а не постоянный reusable admin key. Первичное сопряжение не зависит от ещё не полученных Tailnet/AWG-настроек. У каждого устройства собственные ключи и идентичность; Auth key Tailscale не является ключом подписи приложения.

Использовать стандартные криптобиблиотеки: шифрование payload, подпись автора/издателя. Envelope включает group ID, эпоху, автора, operation/revision ID, схему, минимальную версию клиента, hash, причинный контекст и назначение профиля. До применения проверяются права, подпись, целостность, anti-replay, размер и совместимость.

Показывать полученную, объединённую и применённую версии отдельно. Проверка схемы/ссылок → dry-run генератора → атомарное применение → проверка активного пути/откат. Обычное обновление не рвёт туннель без разрешённой политики; срочные изменения задаются явно. Ошибка сохраняет последнюю рабочую конфигурацию.

Нужны журнал правок, просмотр/разрешение конфликтов, восстановление версии, «Синхронизировать сейчас», последняя успешная связь и причина ожидания. Не писать «синхронизировано», если конфигурация получена, но не применена.

Отзыв блокирует новые операции и выдачу новых ключей; при необходимости ключи ротируются. Удаление уже полученных данных с офлайн-устройства не гарантируется. Старые операции после отзыва/смены эпохи не применяются автоматически. При выключенном главном посредник может хранить уже подписанную ревизию, но не создавать новую. Изменение AWG канала требует поэтапной активации и восстановления связи с офлайн-участниками.

## 10. Встроенный Tailnet и AmnesiaWG

Цель — доступ к своему Tailnet и обмен настройками при одновременно работающем основном proxy/VPN в одном Android-профиле. Запуск отдельного Tailscale VPN вместо текущего VPN не выполняет это требование. Исследуемая архитектура: один VpnService, общий диспетчер маршрутов и встроенный userspace/netstack-адаптер. Для первых собственных sync-соединений приложения рассмотреть tsnet; системный доступ ко всему Tailnet требует отдельной интеграции.

Переиспользовать существующий AWG через mihomo. Дополнительно исследовать транспорт Tailnet с обфускацией AmnesiaWG 1.5+; перед реализацией закрепить конкретную совместимую пару версий и параметров, а не обещать любую комбинацию «1.5+».

Первый кандидат из ТЗ — [LiuTangLei/tailscale-awg-installer](https://github.com/LiuTangLei/tailscale-awg-installer). Это установщики/документация; код искать в [LiuTangLei/tailscale](https://github.com/LiuTangLei/tailscale), мобильную обвязку — в [LiuTangLei/tailscale-android](https://github.com/LiuTangLei/tailscale-android), используемый transport — в [LiuTangLei/wireguard-go](https://github.com/LiuTangLei/wireguard-go). Предыдущее исследование Orrdroid фиксирует v1.104.4; перед переносом нужен аудит конкретного release tag/commit и зависимостей, а не предположение о содержимом main.

Разделить две архитектуры: нативный AWG-транспорт выбранного форка Tailscale и внешний AWG-путь до собственного шлюза через mihomo. У них разные требования к peers и маршрутам. Проверять control plane, прямые peer-соединения, DERP, DNS, UDP, MTU, отсутствие рекурсии и утечки при отказе AWG. Совместимость с Tailscale/Headscale control plane не доказывает связь с немодифицированными peers при любых AWG-параметрах. Смешанная сеть проверяется отдельно. QUIC из возможностей внешнего форка не включать автоматически без отдельного обоснования и тестов.

В Karing есть настройка Tailscale Auth key; использовать её как ориентир UX, не считать перенос sing-box-обвязки готовым адаптером Xray/mihomo. Auth key регистрирует узел, а не синхронизирует настройки и не подписывает общий профиль. Node state/private key не переносится между устройствами.

Полное ТЗ включает остальные функции оригинального Tailscale. Зафиксировать версию оригинального клиента, составить инвентаризацию и вести проверяемую матрицу паритета:

| Область | Целевой результат |
|---|---|
| Регистрация и жизненный цикл | Вход/выход, аккаунты, Auth key, собственная идентичность, хранение ключей, повторное подключение |
| Узлы Tailnet | TCP/UDP к узлам, входящие соединения по политике, MagicDNS, соблюдение ACL/grants |
| Маршруты | Subnet routes, выбор exit node, конфликты маршрутов и DNS с основным proxy |
| Транспорт | Различение direct/DERP, работа после смены сети, AWG между совместимыми peers и поведение при отказе |
| Функции оригинального приложения | Sharing/Taildrop и все остальные функции зафиксированной версии; по каждой — поддерживается, планируется либо явное ограничение |

Полный функциональный паритет остаётся целью ТЗ. Неподдержанная функция фиксируется как незакрытое требование/ограничение; один успешный вход не означает выполнения всего пункта.

Зафиксировать версии ядра, мобильной обвязки и WireGuard/QUIC/uTLS-зависимостей. В матрицу включить несовпадающие AWG-профили, auth expiry, IPv4/IPv6, смену сети, рестарт и восстановление state. Проверять HTTPS/файл/UDP к Tailnet-назначению: одного `tailscale ping` недостаточно. Control plane и data plane принимаются раздельно.

Первый прототип должен передать подписанную тестовую конфигурацию между двумя встроенными Tailnet-узлами при работающем proxy. Следующий проверяет общий TUN, TCP/UDP, MagicDNS, AWG, DERP и смешанных peers. Команда `tailscale awg sync` внешнего форка не заменяет протокол синхронизации приложения из §9.

## 11. Рабочий профиль, защита TUN и аудит безопасности

Цель — устранить подтверждённые несанкционированные пути передачи и доступа к управлению. [RKNHardering](https://github.com/xtclovver/RKNHardering) использовать как каталог проверок. Различать обнаружение признаков VPN, передачу данных через чужой TUN и доступ к локальному SOCKS/HTTP/API: это разные результаты. Не обещать скрытие TUN или TRANSPORT_VPN от всех приложений обычным APK; root/системные вмешательства не входят в базовый клиент.

В Keqdroid уже есть ConnectionOwnerServer, owner guard и патчи Xray/mihomo/sing-tun. Сначала проверить существующую реализацию, применённые патчи, генерируемую конфигурацию и поставляемые бинарники; не писать второй механизм до воспроизведения пробела. Обновлённые JVM/Robolectric-тесты не заменяют испытания межпрофильного трафика на устройстве.

IP-пакет TUN не содержит UID. Определение владельца TCP/UDP средствами Android может завершиться неизвестностью или ошибкой; остальные протоколы требуют отдельной политики. Прямое требование «обращения из рабочего профиля отбрасываются по UID» реализовать как проверяемый контракт разрешённых/запрещённых потоков, без обещания универсального UID для любого пакета.

Контракт строгого режима:

- До подтверждения разрешённого происхождения прикладные данные не уходят через защищённый выход. Очередь ожидания ограничена по времени, потокам и памяти; переполнение не разрешает передачу.
- Различать allowed, denied, unknown, lookup_failed и unsupported. Неизвестный/ошибочный lookup не превращается в разрешение; системные исключения имеют отдельное проверяемое основание.
- При отказе owner service показывать «изоляция не подтверждена» и восстанавливать службу/туннель; автоматически отключать защиту нельзя.
- Проверять исходные адреса потока до проксирования, DNS hijack и переопределения назначения. Не считать любой Xray-путь обязательно проходящим через tun2socks.
- Для системного DNS/Private DNS, ICMP, фрагментов, IPv6 extension headers, PMTU и входящих Tailnet-соединений нужна отдельная политика.
- Совместимый режим с известными ограничениями отличается от строгого явно; скрытое переключение между ними запрещено.

Ранняя матрица аудита: основной↔рабочий профиль, Private Space, allProxy/include/exclude, оба ядра, штатные и импортированные конфигурации, AWG и цепочки. Проверить принудительную привязку чужого приложения к TUN, TCP/UDP IPv4/IPv6, системный/внешний DNS по TCP/UDP:53, A/AAAA/TXT/CH/HTTPS, DoT:853, localhost endpoints в том же и соседнем профиле. Исключение по DNS-адресу не считается доказательством системного происхождения.

Отдельные отрицательные сценарии: INVALID_UID/закрытый сокет, timeout/обрыв IPC, исключение API, недоступная служба; повтор 5-tuple другим сокетом, новый SYN, смена списка приложений/сети и политики, лавина запрещённых потоков, переполнение очереди. Измерять очистку кэша, задержку нового соединения, UDP loss, CPU и память. Проверять Android/ROM, включая сценарии из материалов CalyxOS/GrapheneOS и различия до Android 17/17+, без переноса одного результата на все устройства.

Дополнительный аудит: фильтрация опасных секций импортированных конфигов, закрытые управляющие API, аутентификация необходимых listener, минимизация exported Android-компонентов, защита токенов/backup, отсутствие секретов в логах, подписи обновлений и происхождение зависимостей. Проверить DNS/IPv6/UDP и выход при запуске, смене режима, узла и падении ядра. Не отключать TLS-проверку и не менять MTU на 1500 только ради прохождения детектора; проверять PMTU/MSS и реальные передачи.

Разрешённый аутентифицированный LAN-inbound и собственный Tailnet/sync не являются разрешением чужого TUN. Их работа проверяется без ослабления owner guard. Критерий закрытия: разрешённые сценарии работают, запрещённые потоки не доходят до контролируемой цели, отказ проверки не открывает строгий режим. Видимый tun0 или один TCP RST сами по себе не доказывают утечку внешнего IP. Гипотезы по прежним версиям подтверждаются повторно на выбранной сборке.

## 12. Фоновая работа, архитектура, совместимость и диагностика

Мониторинг должен работать при закрытом Flutter UI, выключенном экране, Doze, сетевых переходах и частичном отказе отдельных маршрутов. Выбор фонового Dart isolate либо нативного исполнителя принимается после изучения текущего сервиса. Поведение Farvater не считается готовой гарантией непрерывного мониторинга Android; нужны испытания OEM/энергосбережения.

Сохранить восстановление сессии Keqdroid после системного перезапуска сервиса/телефона, с учётом сохранённого намерения пользователя, разрешения VPN и совместимого снимка. Отдельно проверить Always-on. Явная остановка пользователем имеет приоритет; случайное восстановление после неё запрещено. При смене сети/БС↔ЧС отменять старые задачи, применять целостный набор правил и DNS, проверять новый путь и не откатываться на запрещённый новой политикой выход.

Разделить ответственность, переиспользуя существующие компоненты:

| Компонент | Ответственность |
|---|---|
| NetworkContext | Физическая сеть/поколение, режим и подтверждённая диагностика |
| ProbeScheduler / Runner | Приоритеты, лимиты, отмена и принудительная проверка конкретного пути |
| HealthStore | Контекстная история, свежесть и структурированные ошибки |
| CandidateSelector | Допуск отдельно от ранжирования |
| AutoController | Отказ, восстановление и улучшение; согласование всех групп |
| RouteCompiler | Единая модель → Xray/mihomo, совместимость, DNS и объяснение маршрута |
| SwitchExecutor | Подготовка, применение, проверка действующего пути и допустимый откат |

Алгоритм должен воспроизводиться на сохранённой последовательности событий без реального VPN. Два несогласованных управляющих цикла недопустимы. Состояния интерфейса: «работает», «проверяем соединение», «ищем резерв», «нет доступа к сети», «переключаем», «частичный доступ». Журнал содержит причину, старый/новый путь, результаты и время восстановления, без секретов.

Переиспользовать обе модели конфигураций, адаптеры, импорт и backup Keqdroid. Новые поля получают версию схемы, миграцию и обратимо проверяемый экспорт/импорт; старые маршруты — «Всегда». Неизвестная новая схема отклоняется понятно, downgrade не читает её как старую. Сохранять стабильные ID и порядок; импорт старого backup сначала проверять в копии.

Android без root — первая платформа реализации; существующие настольные возможности не терять, новые функции принимать отдельно на desktop/TV. Выбор ядра определяется всем графом конфигурации. Не заявлять поддержку каждого протокола в обоих ядрах.

До реализации каждой функции искать совпадающий механизм в Keqdroid и подходящие решения Farvater/Karing/других открытых проектов. Сохранять авторство и применимые лицензии при переносе. Для форка Orrdroid — отдельные package ID, ключ подписи и независимая версия; репозиторий разработки и выпусков — [orrtyom/orrdroid](https://github.com/orrtyom/orrdroid). Эти организационные решения форка не требуют переименования оригинального Keqdroid.

Зафиксировать upstream commit, версии ядер, схему backup, Android versionCode, миграции и известные ограничения каждого выпуска; проверять upstream обновления отдельно. Секреты подписи, реальные подписки, ключи, UUID и сырые пользовательские логи не коммитить. Использовать синтетические fixtures, воспроизводимую сборку и существующие Flutter/Android проверки.

Сначала стабильные ID/миграции и контракт проб, затем допуск Auto; ручной режим до автоматического; проверка конкретного выхода до обязательной географии; полный путь до динамической цепочки. LAN/file-sync может разрабатываться независимо от Tailnet-прототипа. Архитектуру и сроки неопределённых частей уточнять после прототипов, не исключая их из ТЗ.

| Область | Условие приёмки |
|---|---|
| Первый запуск / режим | Сопоставлены чистая установка, кэш, импорт, неизвестный режим, ручной выбор, «Галс», смена сети и восстановление; старая задача не перезаписывает новый выбор |
| Маршруты БС/ЧС | Верный порядок, DNS и «Всё остальное»; недоступный обязательный выход не превращается в отсутствие совпадения |

| Принудительный путь | Проверены реальный кандидат/полная цепочка и её страна; текущий GlobalAuto или DIRECT не подменяют пробу |
| GlobalAuto | Рабочий узел найден среди разрешённых подписок независимо от позиции; исключённые узлы не возвращаются при пустом пуле |
| Фильтр списка | Опционален, не удаляет узлы, различает непроверенные/устаревшие/неуспешные; повторные проверки продолжаются |

| Улучшение пути | Порог/удержание/подтверждение соблюдены; авария не ждёт таймера улучшения; нет колебаний и бесконечного перебора |
| Цепочки | Работают все поддерживаемые комбинации, DNS/UDP и нужный выход; удаление/несовместимость/отказ ступени дают явное решение без скрытого упрощения |
| Провайдеры и списки | Refresh сохраняет пользовательские overrides, ID, порядок и выбранные правила; ошибки загрузки не уничтожают рабочую базу |
| LAN | Без credentials/с неверным паролем отказ SOCKS5/HTTP/CONNECT; URI/QR совпадают, смена сети не публикует listener, API недоступно, UID-защита сохранена |
| Синхронизация главного | Ведомое не меняет главное через любой канал/backup; офлайн и утрата главного не повышают права |
| Все устройства | Независимые правки сохраняются, повтор идемпотентен, конфликт порядка/секретов виден, старое устройство не воскрешает удалённые объекты |
| Каналы и отзыв | Конкурентные uploads/rollback/пропуски обнаруживаются; ключи/эпохи/отзыв работают; полученная версия не считается применённой |
| Tailnet/AWG | Обмен при работающем proxy, TCP/UDP/MagicDNS/ACL, subnet/exit routes, direct/DERP, совместимые AWG peers, отказ и смешанная сеть; отдельная проверка каждой функции паритета |
| Изоляция | Запрещённые реальные потоки не доходят до контролируемой цели; ошибка owner lookup не разрешает строгий режим; разрешённые DNS/PMTU/LAN/Tailnet работают по политике |
| Жизненный цикл | Закрытый UI, сон/Doze, Wi-Fi↔LTE, смерть ядра/сервиса, перезагрузка, Always-on, ручная остановка, обновление/удаление объектов во время проверки |
| Совместимость | Старые backup, оба ядра, штатный/готовый конфиг, AWG, цепочки, REALITY и DNS; новые функции не ломают уровень 0 |

Главные метрики — доступность нужных сервисов, время без связи, p50/p95 восстановления, ложные переключения, обрывы длительных TCP/UDP-сессий, фоновые показатели и стоимость проверок: байты, CPU, память, временные ядра/сокеты, батарея. Проверять ресурсы и длительный прогон, включая сутки работы и множество connect/disconnect; сравнивать на одинаковой сети, конфигурациях и версиях ядер. Сохранённые ping из разных backup не являются A/B-тестом. Низкий RTT не компенсирует недоступность или рост числа обрывов.

Предварительные количественные критерии из плана испытаний:

- Все детерминированные сценарии переходов, миграции и безопасности проходят; в проверенной матрице нет потери конфигурации и неразрешённой передачи.
- При контролируемом отказе, живой физической сети и заранее проверенном резерве — целевой p95 восстановления ≤30 секунд. Для Doze/OEM условия и результаты приводятся отдельно.
- Восемь часов стабильной сети без ложных аварийных переключений; добровольные смены соответствуют политике.
- 24–48 часов смешанной нагрузки со screen-off, Wi-Fi/LTE и рестартами без необратимого зависания и роста числа процессов/памяти.
- Начальный энергетический ориентир — не более 10% относительного роста расхода против базового Keqdroid при одинаковом сценарии. Бюджет принимается либо корректируется по исходным измерениям.
- Исчерпание заданного бюджета трафика останавливает исследовательские/скоростные сканы; минимальная диагностика активного пути имеет отдельный учёт.
- Для beta — несколько OEM/версий Android и минимум неделя реального использования с журналом. Для стабильного выпуска — измеренное улучшение доступности/восстановления без регрессии маршрутов, ложных переходов и локальной защиты.
- Для режима главного — запрет обратной записи во всех отрицательных тестах, подпись/anti-replay, атомарность, два разных типа устройств и восстановление после офлайна; до широкой публикации — отдельный аудит криптографического протокола.

Это цели приёмки, а не уже полученные показатели. Повторные проверки после изменений охватывают затронутые сценарии.
